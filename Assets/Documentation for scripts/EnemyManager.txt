CURRENT UPDATE - 2026-09-16  DEAD NUMBERED SIBLINGS REMOVED
Initialize1 and RebuildFromBase1 are deleted. Neither had a call site. Initialize1
differed from Initialize only in NOT setting unitLevel from the stage, so an enemy
built through it never grew with the campaign - reviving it would have silently
disabled enemy scaling entirely.

This file is now the ONLY thing that decides an enemy's strength, and that is the
intended design: statsBase (UnitStatsSO) x ProgressionMath.GetGrowthMultipliers
(unitLevel = stage, from this prefab's own `progression` asset). CPBattleController
no longer rescales enemies to a CP budget - it only reads the result.

Because `progression` is a per-PREFAB serialized field, giving each enemy TYPE its
own growth curve needs no code at all: create one ProgressionConfigSO asset per type
and assign it on that prefab.

================================================================================
  EnemyManager.cs
  Path : Assets/Scripts/Combat/Enemy/EnemyManager.cs
  Type : MonoBehaviour   [DefaultExecutionOrder(-100)]
  Layer: Combat / Enemy
  Scenes: all 7 gameplay stages

PURPOSE
-------
Stage 1-5 addition: FixedUpdate temporarily defers attack actions while the runtime
MeleeContactRecovery component is repositioning after missed weapon contact.

The BRAIN of one enemy: it owns the live stats (via CP/stat rebuild), the target
detection, facing, gate-attack vs player-attack decision, the attack cooldown,
and the death/revive lifecycle. It is the enemy-side counterpart to PlayerManager
combined with the FSM states - except enemies do NOT use a state-machine, all
logic lives directly in this one class as a big if/else per-frame update.

[DefaultExecutionOrder(-100)] makes it initialise before most other scripts,
which matters because Awake resolves the gate reference other systems may need.

REGION: CP / STATS / PROGRESSION
---------------------------------
  statsBase     (UnitStatsSO)          design-time L1 stats
  unitStats     (UnitStatsRuntime)     live mutable stats
  unitLevel     (int, min 1)           progression level (see Initialize below)
  progression   (ProgressionConfigSO)  growth curves
  stageLevel    (int, min 1)           the CP "lens" - set by EnemySpawner
  cpWeights     (CPWeightsConfigSO)
  cp            (int, Debug)           computed Combat Power, visible in Inspector

  _atkM, _defM, _hpM, _mvM, _asM, _rngM  (float, default 1) runtime multipliers,
      the enemy-side equivalent of roguelite buffs

  Initialize(int stageLevelFromSpawner)
      Sets stageLevel AND unitLevel to the same value - this is the key design
      decision: an enemy's progression level literally IS the stage number, so
      enemies naturally get stronger stats.attack/maxHP/etc. as the player
      advances through stages, without any separate difficulty curve.
      Then calls RebuildFromBase().

  RebuildFromBase()
      1. unitStats.FromSO(statsBase) - reset to base.
      2. Apply growth multipliers from ProgressionMath using unitLevel
         (attack, HP, moveSpeed, attackSpeed only - g.gD (defense) is still
         never applied here, which matters because defense is the axis where
         the six enemy archetypes actually differ, 28..78. See D2 in
         Docs/cp-analysis/NEXT_VERSION_CHANGES.md. Range no longer has a growth
         axis at all, so there is nothing missing on that side any more.)
      3. Apply the runtime multipliers via ApplyMultipliers.
      4. Push maxHealth/currentHP into the EnemyStats component so the health
         bar matches.
      5. Recompute cp via UnitCP_WithFallback.

  SetRuntimeMultipliers(atk, def, hp, mv, atkSpd, rng, rebuildNow = true)
      Stores the multipliers and optionally rebuilds immediately.

  AttackCadence(float recoveryTime) -> float
      Seconds between swings = recoveryTime / attackSpeed, attackSpeed floored at
      0.05. All THREE cadence sites in this file use it (the gate-attack path, the
      second gate branch, and AttackTarget). Mirrors PlayerManager.AttackCadence
      exactly - both factions must use the same rule or they run on different
      clocks. Added by B2; before it, attackSpeed only set animator playback speed
      and contributed nothing to damage output.

  UnitCP_WithFallback(stats, stage, cfg)
      Now simply delegates to CPCalculator.UnitCP. The name is historical.
      It used to contain a SECOND, divergent hard-coded weighted-sum formula for
      the case where cfg was null. That branch was deleted with the A1 rewrite:
      CPCalculator.UnitCP no longer needs a weights config, so there is nothing
      to fall back to, and keeping the old branch would have been actively wrong
      - it produced numbers on a completely different scale from the new formula.
      There is now exactly ONE CP formula in the project.

LIFECYCLE
---------
  OnEnable / OnDisable
      Subscribe/unsubscribe PlayerGateStats.OnGateDestroyed -> HandleGateDestroyed.
      Correctly paired, so no leak across spawns.

  Awake()
      Caches components, defaults currentAttack to defaultAttack (so a gate hit
      always has SOMETHING to swing with even before targeting logic runs),
      finds "PlayerCastle" by NAME if currentGateTarget is unassigned (logs an
      error if not found), and remembers the starting Rigidbody2D body type for
      later restoration on revive. Finally calls EnsureDepthSorter().

  EnsureDepthSorter()   [added 2026-09-11]
      Adds a UnitDepthSorter if the object has none, giving the enemy a Y-driven
      draw depth. Every character part in the game sits on sorting layer Default
      at order 1, so without it the tie between two overlapping units resolves
      arbitrarily - which is why an enemy's head could be painted over the hero it
      was fighting. Done in code rather than on the six enemy prefabs so nothing
      can ship without it, including anything the debug stage tools spawn.

  Start()
      Disables the damage collider, applies initial facing, then CACHES the
      scene's RogueliteManager into the `roguelite` field and registers itself
      with it. Both the cache and the call are null-checked, so a scene with no
      RogueliteManager (the older test scenes) is fine. The cache exists because
      the death path in Update() needs the same reference every frame.

  Update()  (the live version)
      1. Respects GameplayPause.
      2. If close to a target (distanceFromTarget < fairDistanceToPlayer),
         updates facing every frame.
      3. If enemyStats.enemyIsdead: calls StopMovingEnemy(), and on the first
         frame of death starts DestroyAfterDelayRealtime(0.5f), then RETURNS -
         no further logic runs once dead.
      4. If the current target has died (currentTarget.playerIsdead), resets
         attack flags so the enemy does not stay locked waiting on a corpse.
      5. Calls DetectPlayerTargets() EVERY FRAME (see below).
      6. HandleRecoveryTimer() and reads the animator's "isInteracting" bool
         back into isInteracting.

  FixedUpdate()
      Respects GameplayPause, then calls HandleCurrentAction().

FACING  (#region Facing)
-------------------------
  UpdateFacing()
      Priority 1: if there is a player target, FacePlayerStable(); else
      Priority 2: SetInitialFacingByScreenHalf().

  FacePlayerStable()
      Computes horizontal delta to the target, ignores it if smaller than
      facingDeadZoneX (prevents flicker when standing almost level), else calls
      ApplyFacing(faceLeft = dx < 0).

  ApplyFacing(faceLeft) / FaceLeft(faceLeft)
      Both flip transform.localScale.x's sign - the standard 2D sprite-flip.

  SetInitialFacingByScreenHalf()
      Uses the main camera's viewport X to decide which half of the screen the
      enemy is on, and faces toward the opposite half (so enemies spawned on the
      right face left, roughly toward the player's side).

STOPPING / DEATH
-----------------
  StopMovingEnemy()
      Zeroes the animator's Vertical/Horizontal floats, hard-stops the
      Rigidbody2D (zero velocity, Kinematic), and DISABLES enemyLocoMotion and
      topDownMover so nothing can write velocity again this frame or later.
      If enemyIsdead, plays "Dying" directly.

  DestroyAfterDelayRealtime(seconds)  [coroutine]
      Uses WaitForSecondsRealtime so the destroy still happens even while
      GameplayPause has set Time.timeScale to 0 - the point being that a paused
      game can still finish clearing a dead enemy off screen once resumed, since
      "seconds" is real time not game time.

TARGETING
---------
  DetectPlayerTargets()
      Physics2D.OverlapCircleAll around detectionRadius on playerDetectionLayer,
      picks the NEAREST live (non-dead) PlayerStats, and writes it into
      enemyLocoMotion.currentTarget - this is the single source of truth for
      "who is this enemy fighting", read by EnemyLocoMotion's movement.

      SINCE 2026-09-12 IT ONLY RUNS THAT SEARCH WHEN THE ENEMY HAS NO TARGET.
      Once an enemy has locked onto a hero it keeps it: a nearer hero does not
      take the target away. StillFightable() below is the only thing that
      releases the lock.

      NO-BACKTRACKING, added 2026-09-21 (Arash). An enemy advances on the player
      base and may engage a hero IN FRONT of it or TO EITHER SIDE, but it must
      never turn round and chase one that has already walked past it. Two places
      enforce it here:
        - ACQUISITION skips any candidate for which IsBehind() is true.
        - THE LOCK gains its one new release: a locked hero that has slipped
          behind is dropped, so the enemy re-acquires or marches on. It is KEPT
          when it is still inside attack reach (finish the fight you are in) or
          when it is the retaliation target.
      Movement is constrained separately, in EnemyLocoMotion - see
      StripBackwardMotion. Both halves are needed: this one stops the enemy
      WANTING to go back, that one stops it physically doing so.

      THE BUG THAT CAUSED THE LOCK. This is called every frame from Update, and
      it used to overwrite currentTarget unconditionally. An enemy in the middle
      of a crowded 4v4 or 5v5 line has heroes on both sides at almost exactly
      equal range, so the nearest-comparison changed winner frame to frame. Every
      swap flips which side of the target the enemy walks to
      (MeleeEngagement.ChooseSide) and flips its facing with it - on screen, a
      unit spinning in place instead of fighting. Reported by Arash from play.

      A HARD LOCK, NOT HYSTERESIS. The hero side has the same hazard and solved it
      with a margin instead: PlayerManager.retargetHysteresis (0.2) makes a new
      enemy have to be ~20% closer before a hero switches. Arash asked for the
      stronger rule on the enemy side. The two are deliberately different; if the
      hero side ever needs the same treatment, it is the same change.

      CONSEQUENCE, ACCEPTED: a locked enemy will walk past a hero standing right
      beside it to reach the one it locked onto. The armies meet as a group in
      this layout, so it is rare - and the alternative is the spinning.

      !! PERFORMANCE: the search allocates a new Collider2D[] (OverlapCircleAll,
      not the NonAlloc variant). It used to do that EVERY FRAME for EVERY enemy
      and was one of the larger recurring GC sources in combat; the lock now skips
      it for any enemy that already has a target, which is most of them for most
      of a battle.

  StillFightable(hero, radius)
      The ONLY three things that release the lock:
        1. the hero is dead, or its object is gone (Unity null check);
        2. the hero is in PlayerLockState - an undeployed unit that
           EnemyDamageCollider refuses to hit, so staying locked on it would leave
           the enemy swinging at something it can never damage;
        3. the hero has left detectionRadius entirely - which is also what lets an
           enemy give up and walk on the base instead.
      ResetAfterRevive() clears currentTarget before calling DetectPlayerTargets,
      so a revive still re-acquires normally.

ACTION DECISION
----------------
  HandleCurrentAction()   (the live version, called from FixedUpdate)
      1. If there is a current player target AND
         enemyLocoMotion.IsInAttackPosition(), and neither it nor this enemy is
         dead: AttackTarget() + UpdateFacing(), then RETURN - player takes
         priority over the gate.

         CHANGED 2026-09-11. This used to be the radial
         `enemyLocoMotion.distanceFromTarget <= enemyLocoMotion.stoppingDistance`,
         which is TRUE for an enemy parked directly above its target. The enemy
         then froze its locomotion and played swing after swing through a hero it
         could not touch, because the weapon box only reaches sideways. Gating on
         the POSITION instead lets it finish walking round to the flank first.
         See MeleeEngagement and EnemyLocoMotion.
      2. Else, if attackPlayerGate is set and the gate is alive: on cooldown
         expiry, sets IsAttacking + isPerformingAction, resets
         currentRecoveryTimer from AttackCadence(currentAttack.recoveryTime),
         i.e. recoveryTime / attackSpeed since B2 (falling back to
         defaultAttack with a warning if currentAttack was somehow null), stops
         the walk animation, and plays the attack animation at
         unitStats.attackSpeed.

         THE IsAttacking LINE IS LOAD-BEARING [fixed 2026-09-06]. It was
         missing, and the castle therefore took ZERO damage: the swing animation
         played in full, the animation events opened the weapon collider and the
         trigger fired on the castle, but EnemyDamageCollider's castle branch
         gates every hit on enemyManager.IsAttacking and threw the hit away one
         line before ApplyDamageToPlayerGate. Hero-vs-hero damage was unaffected
         because branch 1 goes through AttackTarget(), which raises the flag.
         This branch CANNOT simply call AttackTarget() instead: that method
         dereferences enemyLocoMotion.currentTarget.playerIsdead with no null
         check, and there is no hero target during a gate attack - which is
         presumably why the body was copied inline here and the flag lost in the
         copy. The dead sibling HandleCurrentAction1 still has the same omission.

GATE CONTACT
-------------
  HandleGateDestroyed()
      Clears attackPlayerGate, currentGateTarget and reachedGate, and stops the
      walk animation. Called when PlayerGateStats broadcasts its static event.

  HandleGateTrigger(gate)  /  OnTriggerEnter2D  /  OnTriggerStay2D
      Both trigger callbacks funnel into HandleGateTrigger, which sets
      attackPlayerGate = true, currentGateTarget = gate, and on the FIRST
      contact latches reachedGate = true and records gateStopPosition from the
      Rigidbody2D - this is what EnemyLocoMotion clamps to so the enemy can
      never walk past the gate. Using OnTriggerStay2D as well as Enter means
      the gate reference and stop position self-heal even if Enter is somehow
      missed on the first frame.

DAMAGE
------
  DamageApplying(PlayerManager target) -> float
      CombatMath.DamagePerHit(unitStats, target.unitStats) - the enemy's
      outgoing damage formula, shared with the player side.

ATTACK  (#region Attack)
--------------------------
  HandleRecoveryTimer()
      Counts currentRecoveryTimer down by Time.deltaTime. When it reaches 0
      while isPerformingAction is still true, clears both isPerformingAction and
      IsAttacking - this is the ONLY place IsAttacking is turned off, making it
      the authoritative "attack finished" signal.

  AttackTarget()
      If already performing an action, just zeroes the Vertical float and
      returns (do not restart the swing). If no currentAttack, calls
      GetNewAttack() and returns (try again next call). If the target has died,
      bails out. Otherwise sets IsAttacking/isPerformingAction, starts the
      cooldown from AttackCadence(currentAttack.recoveryTime), zeroes the movement animator
      float, and plays the attack clip at unitStats.attackSpeed.

  GetNewAttack()
      Selects defaultAttack only if distanceFromTarget falls within the attack's
      min/max distance band; otherwise leaves currentAttack null.

  GetNewTargets()
      If there is neither a player target nor a gate target, calls
      HandleCurrentAction() directly - an odd one-off manual poke, not called
      from Update or FixedUpdate itself.

REVIVE
------
  ResetAfterRevive()
      Called after the player revives (paying gems) and the fight resumes.
      Refuses to act if this particular enemy is already dead (a dead enemy
      cannot be "revived"). Clears attackPlayerGate and reachedGate, RE-FINDS
      the PlayerGateStats via FindObjectOfType (falling back to a GameObject.Find
      by name, logging a warning if neither succeeds), resets the Rigidbody2D to
      Dynamic with zero velocity, re-enables enemyLocoMotion and clears its
      target so detection runs fresh, resets action/interaction flags and the
      cooldown timer, and finally calls DetectPlayerTargets() immediately so the
      enemy does not have to wait a frame to reacquire someone.

NO-BACKTRACKING API  (added 2026-09-21)
------------------------------------------------------------------------------
  behindTolerance   (float, default 0.35)  how far behind the enemy a hero may
      be and still count as BESIDE it rather than behind. Slack, so a hero
      exactly level with the enemy is still engaged and the test does not
      flicker as the two drift past each other.
  retaliationMemory (float, default 3)  how long after being hit the enemy will
      still turn and fight a hero behind it.

  MarchDirection -> Vector2        = -transform.up, the SAME vector
      EnemyLocoMotion marches along, so "behind" is measured against the real
      direction of travel rather than an assumed world axis. (A rotated enemy
      therefore behaves correctly; nothing in the project rotates them today.)

  IsBehind(worldPos) -> bool
      Dot(toTarget, MarchDirection) < -behindTolerance. The half-plane strictly
      behind the enemy. In front and both sides return false.

  RetaliationTarget (PlayerStats, read-only) + IsRetaliationTarget(hero)
      The one hero this enemy will turn round for: whoever last hit it, for
      retaliationMemory seconds. It still does not WALK back - it only faces
      and attacks in place.

  NotifyAttackedBy(PlayerManager)
      Called from EnemyStats.ApplyDamageToEnemy on every blow. Resolves the
      attacker's PlayerStats and starts the retaliation window.

HOW IT CONNECTS
---------------
  - Reads UnitStatsSO/UnitStatsRuntime/ProgressionConfigSO/CPWeightsConfigSO -
    the whole Data layer.
  - Drives EnemyLocoMotion (by writing currentTarget and reading
    distanceFromTarget) and EnemyAnimatorManager (PlayTargetAnimation).
  - Damages PlayerStats and PlayerGateStats through PlayerDamageCollider is the
    reverse path; this class computes the OUTGOING damage number that
    EnemyDamageCollider applies.
  - RogueliteManager.RegisterEnemy links this enemy into the roguelite XP
    system, and Update() now calls RogueliteManager.NotifyEnemyKilled(this) the
    frame it dies, granting XpValue. THIS IS THE ONLY XP SOURCE IN THE GAME -
    it was previously missing entirely, which left the whole level-up / buff-card
    loop dead.
  - PlayerGateStats.OnGateDestroyed drives HandleGateDestroyed.
  - OnAnyEnemyKilled  [ADDED 2026-09-03]  a STATIC System.Action raised from the
    same xpGiven-guarded block, immediately AFTER the NotifyEnemyKilled call, so
    the XP bar and any listener can never disagree about a death. Fired here
    rather than from inside RogueliteManager because that call is skipped
    entirely when a scene has no RogueliteManager (the old test scenes do not) -
    a kill counter hung off it would silently read zero. Static so a HUD listener
    that outlives every individual enemy does not have to find them as they
    spawn. Current subscriber: BattleHudCounters (the skull kill counter).
    SUBSCRIBERS MUST UNSUBSCRIBE IN OnDisable - with domain reload disabled the
    delegate survives a second entry into play mode and would otherwise leak a
    dead listener per run.

NOTES / RISKS
-------------
  - This is the largest live script in the project (794 lines even after the
    2026-08-20 duplicate-class cleanup removed EnemyManager1/EnemyManager2,
    which together held over 1,000 additional lines). It mixes stat
    progression, targeting, facing, combat decision, gate logic and revive
    handling in one class - a strong candidate for splitting if it is ever
    touched again.
  - Numbered-but-unused sibling METHODS remain: Initialize1, RebuildFromBase1,
    UpdateFacing1, FixedUpdate1, HandleCurrentAction1, HandleGateDestroyed1,
    OnTriggerEnter2D1, ResetAfterRevive1. None are called - Unity only invokes
    the exactly-named Awake/Start/Update/FixedUpdate, and the others are dead
    code sitting next to their live twins.
    Update1 WAS in this list and has now been DELETED, since the XP hookup landed
    in the live Update() and leaving a stale copy of the death branch next to it
    would be actively misleading.
  - DetectPlayerTargets allocates every frame per enemy (see PERFORMANCE note
    above) - the single largest per-frame GC source among the Combat/Enemy
    scripts.
  - xpValue (float, default 1) is the XP this enemy grants on death, in "basic
    enemy" units. Give elites 2-3 so they visibly fill more of the bar - the
    reference game's elites are worth roughly 2-3x a basic kill. The per-level
    scaling is NOT here; it comes from the growing threshold in RogueliteConfigSO.
  - The xpGiven flag guards the once-per-death work: awarding XP and starting the
    despawn coroutine. It is named for the XP grant, which for a long time was
    missing - the flag guarded only the despawn.
  - "PlayerCastle" and the "PlayerGate" tag are magic strings/names on which
    Awake and revive both depend; renaming either silently breaks gate
    targeting.
