CURRENT UPDATE - 2026-09-14  A GATE-LOCKED ENEMY NO LONGER IGNORES HEROES
HandleMoveToTarget's first branch used to pin the enemy Kinematic on
gateStopPosition and RETURN, before the hero-target branch ran at all. So the
moment an enemy touched the gate trigger it stopped seeing heroes ENTIRELY - it
walked to the base and stood there while a hero circled it. Reported three times
running as "near the base the enemy doesn't see the hero at all".

It now breaks off the gate line for a live hero within `fairDistanceToPlayer`
(1.90 on every enemy prefab) - the SAME distance the mid-field branch uses, so
behaviour by the base matches behaviour anywhere else - and re-forms on the line
when that hero is gone or dead. It WALKS back to the line rather than snapping,
because an enemy that chased a hero a metre off it would otherwise teleport.

WHAT THIS BUG WAS NOT (all measured 2026-09-14, so nobody re-checks them):
  - not speeds: hero and enemy moveSpeed are both 0.60 by design
  - not detection: detectionRadius 20, playerDetectionLayer = PlayerLayer, and
    there is NO field of view (EnemyManager's +-60 angles are declared and never
    read by any code)
  - not tags: every hero prefab is tagged "Player", so CompareTag passes
  - not ranges: enemy attackRange 0.83 / stoppingDistance 0.83, hero 0.85
  - not target PRIORITY: EnemyManager's live HandleCurrentAction already checks
    the hero target before the gate

!! THE REAL CONSTRAINT TO REMEMBER IS fairDistanceToPlayer = 1.90. Outside it an
enemy marches straight down its lane (moveDir = -transform.up) EVEN WHEN IT HAS A
HERO TARGETED. With both sides at 0.60 moveSpeed a hero approaching from the side
cannot force its way inside 1.90 on its own, so this value - not detection - is
what decides whether a fight starts. Raise it if enemies still walk past heroes.

PURPOSE
-------
2026-09-11 (later same day) the "hold position while a hero is engaging us" branch
was REMOVED. It stopped the enemy as soon as a committed hero came within
maxAttackRange + 0.35 - up to 1.20 world units, while this enemy's own stand point
is at 0.71 - so the enemy visibly froze BEFORE the hero arrived and stood there with
its walk cycle running. It had been added to kill a magnetic pull that actually came
from MeleeContactRecovery, and that is where it is handled now (the recovery yields
to a hero engaging this enemy). Required behaviour, confirmed by simulation: the
enemy walks until MeleeEngagement.InAttackPosition is TRUE, then stops, then swings.

Retained from that same day: StopAtCurrentPosition explicitly clears linear/angular
velocity; approach steps clamp to the destination with MoveTowards to avoid
overshoot; IsInAttackPosition accepts up to 0.02 extra vertical alignment tolerance
when the engaged hero has reached its own legal attack position, while still
requiring the enemy's own radial reach and minimum spacing. That covers the
0.85/0.83 Valkyrie/enemy range mismatch without enlarging any weapon hitbox.

The LIVE 2D enemy movement driver. Enemies march down the lane toward the
player's gate, optionally divert to chase a nearby player unit, and stop
permanently once they reach the gate. (The older 3D EnemyLocomotionManager is
not used.)

INSPECTOR FIELDS
----------------
  enemyRigidbody2D     (Rigidbody2D) resolved in Awake if unset
  currentTarget        (PlayerStats, HideInInspector) the player unit being chased
  distanceFromTarget   (float) published for EnemyManager to read
  playerDetectionLayer (LayerMask) visual only - detection logic lives in
                       EnemyManager
  detectionRadius      (float, default 6) gizmo radius
  moveSpeed            (float, default 1.5) FALLBACK ONLY since B1. Prefabs
                       serialize 0.2 here, but the real speed is CurrentMoveSpeed.
  stoppingDistance     (float, default 0.5) how close before halting

  CurrentMoveSpeed     (property, float)
                       enemyManager.unitStats.moveSpeed when the stat block is
                       built and > 0, else the serialized moveSpeed. All five
                       movement sites in this file use it. Before B1 the
                       Inspector value was the silent authority and the stat was
                       never read, which is why the sheet said 2.9-3.5 while
                       enemies crawled at 0.2. The SO value is now 0.3.
                       moveSpeed does NOT grow (2026-09-10): ProgressionMath has
                       no gMv at all, so this is a flat 0.3 at every stage and for
                       every unit on both sides. An earlier note here warned that
                       growing enemy moveSpeed would make enemies outpace heroes
                       late in the campaign, since enemy level = stage number.
                       Removing the growth axis is exactly what fixed that.
  fairDistanceToPlayer (float, default 1.6) only chase a player unit within this
                       distance - stops enemies being pulled far off their lane

LIFECYCLE
---------
  Awake()  caches EnemyManager, Rigidbody2D, a child Animator and (if present at
           that moment) MeleeContactRecovery
  Start()  forces correct top-down 2D physics:
               gravityScale = 0, freezeRotation = true,
               interpolation = Interpolate

  BindContactRecovery(recovery)
      Called by MeleeContactRecovery from ITS Awake. Required because
      CPBattleController ADDS that component at runtime on stages 1-5, long after
      this script's Awake has run, so the GetComponent above finds nothing.

  RecoveryOwnsBody  (property, bool)
      TRUE while MeleeContactRecovery is physically stepping this enemy sideways.
      FixedUpdate stands down when it is set. See NOTES - this is the fix for the
      "enemy slides into the hero" bug.

  Update()
      Respects GameplayPause.IsPaused. Republishes distanceFromTarget only
      (20f when there is no target, i.e. "very far"). NO MOVEMENT - see NOTES.

  FixedUpdate()
      Respects GameplayPause.IsPaused, yields if RecoveryOwnsBody, then calls
      HandleMoveToTarget(). All movement is on the physics clock and uses
      Time.fixedDeltaTime, so an enemy walks at exactly its stat speed regardless
      of frame rate.

NO-BACKTRACKING (added 2026-09-21, Arash)
------------------------------------------------------------
An enemy advances on the player base. It may step FORWARD or SIDEWAYS onto a
hero, but it must never reverse to chase one that has walked past it. Only
being hit makes it turn round - and even then it fights IN PLACE.

  StripBackwardMotion(from, to) -> Vector2
      Returns the step with any component against EnemyManager.MarchDirection
      projected out, keeping the perpendicular part. Deliberately NOT a
      cancel-the-whole-step test: the lateral part must survive so the enemy
      still slides across to a hero beside it. A hero directly behind yields a
      zero-length step, and the caller then holds position instead of moving.
      Falls through unchanged when there is no manager to ask.

The targeting half of the rule lives in EnemyManager (IsBehind, the acquisition
filter and the lock release). BOTH are needed: that one stops the enemy WANTING
to go back, this one stops it physically doing so - a hero can walk past after
the lock was taken, and a stand point beside a hero can itself sit behind.

HandleMoveToTarget()  - the live version, evaluated in order
------------------------------------------------------------
  1. GATE LATCH
     If enemyManager.reachedGate is true and there is NO live hero target,
     walk back to enemyManager.gateStopPosition (never snap) and pin Kinematic
     on arrival.
     WITH a live hero target, since 2026-09-21 the enemy NO LONGER chases:
     it holds gateStopPosition, and EnemyManager.UpdateFacing turns it to the
     hero while the attack controller hits from there. Previously this fell
     through to the pursuit branch, which walked the enemy off the gate line
     after any hero that came near - including one standing behind it.
     Consequence, accepted: a hero that stays just outside attack reach of a
     gate-parked enemy is never chased.

  2. ENGAGE A PLAYER UNIT
     If currentTarget exists and is not dead:
       - FIRST, if MeleeEngagement.InAttackPosition(pos, targetPos,
         stoppingDistance) - already standing somewhere the weapon can reach -
         go Kinematic and stop. This replaced a bare radial
         `dist <= stoppingDistance`; see NOTES.
       - isRealPlayer = currentTarget.CompareTag("Player") - the gate uses the
         tag "PlayerGate", so this distinguishes a real unit from the gate
       - withinFair   = dist <= fairDistanceToPlayer
       - If both, walk to ResolveStandPoint(targetPos): a spot BESIDE the hero.
         Arriving within 5 cm of it also stops and goes Kinematic.
       - Otherwise keep marching straight down the lane (-transform.up).
     Body becomes Dynamic and moves with MovePosition at
     CurrentMoveSpeed * Time.fixedDeltaTime.
     SINCE 2026-09-21 the computed step is passed through
     StripBackwardMotion() before MovePosition, and a step that comes back
     empty stops the enemy where it stands instead of moving it.

  ResolveStandPoint(targetPos)
     Claims an AttackSlotRegistry slot on the target the first time (released in
     OnDisable, and re-claimed when the target changes), re-derives the side from
     this enemy's OWN position via MeleeEngagement.ChooseSide with
     EnemyPreferredSide, and returns MeleeEngagement.StandPoint.

  IsInAttackPosition()
     Public. The same test as above, read by EnemyManager.HandleCurrentAction so
     the enemy cannot start a swing while still walking round to the flank.

  3. MARCH TO THE GATE
     With no player target, and the gate alive:
       - if distance to the gate <= enemyManager.gateStopDistance, latch
         reachedGate = true, record gateStopPosition, go Kinematic and stop.
         (A distance-based fallback in case the trigger never fired.)
       - otherwise keep walking along -transform.up.

  SetAnimMoving(bool)
      Sets Horizontal = 0 and Vertical = 1 (walk) or 0 (idle), driving the blend
      tree. Null-safe if no Animator is present.

  OnDrawGizmosSelected()
      Draws the detection radius as an orange wire sphere.

HOW IT CONNECTS
---------------
  - Reads EnemyManager.reachedGate, gateStopPosition, gateStopDistance and
    currentGateTarget - the manager owns the state, this script owns the motion.
  - Publishes distanceFromTarget back for the manager's attack decisions.
  - Honours GameplayPause.

NOTES
-----
  - CHANGED 2026-09-11, three related fixes for a reported bug (enemy slides into
    the hero, both sprites overlap, neither takes damage):

    (a) MOVEMENT MOVED FROM Update() TO FixedUpdate(). MovePosition is a physics
        call, and driving it from Update with Time.deltaTime made the step size
        depend on the frame rate: each physics step moved the body by whatever the
        LAST Update wrote, so an enemy travelled speed * (deltaTime * 50) per
        second - about 83% of its stat speed at 60fps and about 167% of it, in
        steps twice as long, whenever the frame rate dipped to 30. Those oversized
        steps are the forward "skating" that was reported. Expect enemies to move
        at their true authored speed now, which is a small pacing change.

    (b) FixedUpdate YIELDS WHILE MeleeContactRecovery IS REPOSITIONING.
        EnemyManager.FixedUpdate and PlayerManager.FixedUpdate already did this,
        but enemy MOVEMENT does not live in EnemyManager - it lives here. So the
        recovery called MovePosition toward a spot beside the hero in FixedUpdate
        while this script called MovePosition straight AT the hero in Update, and
        Update runs after FixedUpdate, so this script won the race every time: the
        enemy ignored the sidestep and glided into the hero. Heroes never showed
        the same thing because their mover is inside the FixedUpdate that yields.

    (c) THE STOPPING RULE IS NO LONGER RADIAL. `dist <= stoppingDistance` is TRUE
        for an enemy parked directly ABOVE its target, which is the natural result
        of marching down a lane into a hero walking up it - in range, sprites
        merged, and unable to land a hit, because the enemy weapon box is a wide
        flat trigger (Enemy_Orc: 6.58 x 1.19 local, offset +2.79 on X) that only
        reaches sideways. MeleeEngagement.InAttackPosition adds "not sunk into the
        target" and "level enough to connect" to the distance test, and
        ResolveStandPoint walks the enemy round to the hero's flank instead.

  - There is an unused field 'enemyPassedPlayerInY' - REMOVED with the rewrite of
    the chase branch; the rule it belonged to ("enemy tracks player only after it
    has passed the player in Y") had already been commented out of the condition.
  - The dead numbered variants Update1() and HandleMoveToTarget1() were DELETED
    on 2026-09-11. Both still drove the body from the frame clock and
    HandleMoveToTarget1 carried its own separate (also radial) stopping rule - a
    second place to get the enemy approach wrong.
  - The lane direction is hard-coded to -transform.up, so enemy prefabs must be
    rotated correctly or they will walk the wrong way.
  - stoppingDistance doubles as this enemy's "attack range" everywhere:
    MeleeEngagement derives the standoff and band from it, and
    MeleeContactRecovery reads it as the unit's range. Live prefabs author 0.83.
