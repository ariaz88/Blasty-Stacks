PURPOSE
-------
The one and only gateway to persistence. It keeps a single cached SaveData object
in memory, serializes it to JSON with JsonUtility, and stores that JSON in ONE
PlayerPrefs key ("GAME_SAVE_V1"). Every system that needs to remember something
goes through here - gameplay code must never touch PlayerPrefs directly for save
data.

STATE
-----
  _cache     (SaveData)  the single in-memory copy
  KEY        "GAME_SAVE_V1"  the PlayerPrefs key holding the whole JSON blob
  saveDepth  (int)  re-entrancy counter for the recursion guard

  Data  ->  SaveData
      Lazy accessor:  _cache ??= LoadInternal()
      The first read of Data triggers a load from PlayerPrefs.

UNIT PERSISTENCE
----------------
  GetUnitEntry(unitId)      LINQ FirstOrDefault lookup, may return null
  EnsureUnitEntry(unitId)   creates a default entry (locked, level 1) if missing

  SetUnitLevel(unitId, level)
      Clamps to >=1, writes only if changed, then auto-saves.

  SetUnitUnlocked(unitId, unlocked)
      Writes only if changed. Locking a unit also forces isDeployed = false,
      so a locked unit can never remain on the deployed team.

  SetUnitDeployed(unitId, deployed)
      Deploying a unit IMPLIES unlocking it (marked [FIX] in the source).
      Writes only if changed, then auto-saves.

  SetUnitOrders(deployedOrder, undeployedOrder)
      Bulk-saves the player's card arrangement. Sanitizes both lists: drops
      negative ids and removes duplicates. Null input becomes an empty list.

TUTORIALS
---------
  IsTutorialCompleted(tutorialId) -> bool
      Has this tutorial already been shown? Empty id returns false. Lazily
      creates the list, because saves written before this field existed
      deserialize it as null.

  SetTutorialCompleted(tutorialId, completed = true)
      Adds or removes the id, then Save(). No-ops when the flag already matches,
      so it never writes for nothing.

  ResetTutorials()
      Clears the list so every tutorial plays again. Debug / testing only -
      reached from Tools/Tutorial/Reset Tutorial Progress.

  Keyed on TutorialSequenceSO.TutorialId, so RENAMING that id makes every
  existing player see that tutorial again. See TutorialManager.

BATTLE ALLOWANCE
----------------
  GetBattleEnergy()  ->  SaveData.BattleEnergyState
      Read-only accessor for the BATTLE button's daily window. Lazily creates
      the section when it is missing, because saves written before this field
      existed deserialize it as null.

  SetBattleEnergy(windowStartUtc, battlesUsed, energy)
      The single write path for that section. Null timestamp becomes "", the
      two counters are clamped to >= 0, then Save() runs. Only
      BattleEnergyService should call this.

CURRENCY
--------
  SetCoins / SetGems / SetHeroXP   clamp to >=0 and auto-save
  GetCoins / GetGems / GetHeroXP   plain reads

STAGE / LEVEL PROGRESS
----------------------
  EnsureLevel(levelId, stagesPerLevel) -> LevelProgress
      Finds or creates the record for a level. If the stars array exists but is
      the wrong length it is RESIZED while preserving existing stars, and
      highestUnlocked is re-clamped. This makes it safe to change the number of
      stages per level later without wiping player progress.

  GetHighestUnlocked(levelId) -> int      0 if the level is unknown
  GetStars(levelId, stageIndex0) -> int   0 if out of range

  RecordStageResult(levelId, stageIndex0, stars)
      The live scoring entry point.
      - clamps stars to 0..3
      - keeps only the BEST result ever achieved for that stage
      - if stars >= 1, unlocks the next stage
      - saves

SAVING
------
  Save()
      Stamps savedAtUtc, serializes Data to JSON, writes the PlayerPrefs key and
      calls PlayerPrefs.Save(). Wrapped in a recursion guard: if saveDepth
      exceeds 10 it logs an error and returns instead of saving.
      UNCONDITIONAL since 2026-09-22. The SavePersistence debug gate that used to
      short-circuit this method (2026-09-20 to 2026-09-22) is DELETED - every
      call writes to disk, so saving is fully automatic and nothing in the UI has
      to ask for it.

  ResetAll()
      Deletes the "GAME_SAVE_V1" key and nulls the cache. NOTE it does NOT touch
      LevelManager's separate "LM.CurrentStage" - use WipeAllProgress for that.

  WipeAllProgress()  [added 2026-09-22]
      A true "new install": deletes BOTH progress keys ("GAME_SAVE_V1" and
      LevelManager.PlayerPrefsKey), flushes PlayerPrefs and nulls the cache, so
      the next read of Data returns a brand-new SaveData. Because
      completedTutorials rides in the same blob, this also makes MenuLoader
      replay the first-run tutorial - which is the point of "reset".
      Two callers, one implementation: Tools/Save System/Wipe Saved Progress Now
      (SavePersistenceMenu.WipeNow) and GameStartManager's editor-only
      resetProgressOnPlay tickbox in StarterScene.

  LoadInternal()  [private]
      Returns a fresh SaveData if no key exists. Otherwise deserializes the JSON.
      Always reads disk since 2026-09-22 (the SavePersistence gate that used to
      make it ignore the blob is deleted). A "new player" run therefore means an
      ACTUALLY EMPTY key - wipe it with Tools/Save System/Wipe Saved Progress Now.
      Then runs a version-gated migration: for saves with version < 2 it forces
      isDeployed = false on every locked unit, sets version = 2, assigns _cache
      and calls Save(). The _cache assignment MUST stay before Save() - see the
      fixed recursion bug in NOTES.

  ResetAllIfRequested(bool)
      Full "new game" reset used by debug tooling: ResetAll(), then
      LevelManager.ResetProgressToStart(), then resets CurrencyManager, then
      re-seeds PlayerUnits from the units database.
      Currency reset writes GameStartManager.FreshStartCoins/Gems/HeroXp - ALL
      ZERO, and the SAME constants the boot path uses, so a mid-session reset
      and a fresh install cannot disagree about what "new player" means.
      It deliberately does NOT read CurrencyManager's Starting* inspector
      values. It also resets heroXP, which it previously missed.

HOW IT CONNECTS
---------------
  - CurrencyManager mirrors its balances here.
  - GameStartManager reads units[] on boot and writes the seeded roster back.
  - WinPanel / LevelGameManager call RecordStageResult when a stage is won.
  - HomeManager / StageCard read stars and highestUnlocked to build the map UI.
  - SaveOnStop calls Save() on quit and on exiting Play mode (also gated).

NOTES / RISKS
-------------
  - RECURSION BUG (FIXED 2026-08-20). LoadInternal() calls Save() during
    migration, but Save() reads the Data property, and _cache was still null at
    that moment (LoadInternal had not returned yet) - so Data called
    LoadInternal() again. The saveDepth > 10 guard stopped the stack overflow
    but the migration then never persisted, so it re-ran and logged
    "[SaveSystem] Recursion guard: Skipping save" on EVERY launch with a
    version < 2 save. Fixed by assigning _cache = loaded immediately before
    Save(). Do not reorder those two lines. The saveDepth guard is kept as a
    backstop for any other re-entrant path.

  - Almost every setter calls Save() immediately, so a screen that updates many
    units in a loop writes the entire JSON blob once PER UNIT. For bulk edits
    prefer mutating Data directly and calling Save() once at the end.
  - Numbered leftover methods: SetUnitDeployed1 and RecordStageResul1 (note the
    typo) still exist and are still uncalled - the un-numbered versions are the
    live ones. Save1, ResetAllIfRequested1 and ResetAllIfRequested2 were DELETED
    on 2026-09-20 after confirming no call sites; deleting Save1 also removed a
    second write path that bypassed the (now removed) SavePersistence gate.
  - completedTutorials lives in this blob, so wiping the save also makes the
    first-run tutorial play again - which is exactly what MenuLoader keys off.
  - A brand-new SaveData is created with version = 1, so the very first load of
    a fresh save also runs the migration branch. Harmless but wasteful.
  - PlayerPrefs on Android/iOS is not a secure store. Anyone can edit currency.

ADDED FOR THE ONBOARDING TEST SANDBOX (2026-09-23)
--------------------------------------------------
  SuppressWrites (static bool, default FALSE)
      While true, Save() returns immediately: the in-memory cache stays current
      but NOTHING is written to PlayerPrefs. Save() is the single choke point
      every persistence path funnels through, so one guard here covers currency,
      unit levels, stars and tutorial flags alike.

  ReloadFromDisk()
      Drops the in-memory cache (_cache = null), so the next Data read comes
      from disk again.

  THIS IS NOT the save/load toggle deleted on 2026-09-22. That one was a
  user-facing switch that could silently disable saving in the real game. This
  is set ONLY by TutorialSandbox, which lives in the OnBoarding Test scene,
  refuses to arm itself outside the Editor, and in OnDestroy both clears the
  flag AND calls ReloadFromDisk - because by then the cache is full of fake
  numbers and a later save in the same Editor session would otherwise write the
  sandbox wallet into the player's real progress.
