CURRENT UPDATE - 2026-09-17  ACQUIRE ONLY, AND "UNHANDLED" BEATS "NEAREST"
This class no longer switches a living target for a nearer one. Three Inspector
fields and one method were deleted with that behaviour:
    allowNearestSwitch, onlySwitchIfInFront, retargetHysteresis   (fields)
    EnsureTarget1                                                 (dead sibling)
    AcquireNearestEnemy  ->  renamed AcquireBestEnemy
A hero now keeps its enemy until that enemy dies, and picks a new one by FEWEST
OTHER HEROES ON IT first, nearest second. See TargetClaimRegistry.txt for the
rule and PlayerManager.UpdateTargetSelection for the other half of it. The
sections below have been rewritten; nothing under "Retargeting" survives.

================================================================================
  TargetDetectionForPlayer.cs
  Path : Assets/Scripts/Combat/Player/TargetDetectionForPlayer.cs
  Type : MonoBehaviour
  Layer: Combat / Player
  Scenes: all 9 build scenes
================================================================================

PURPOSE
-------
All of the player's enemy-finding logic in one place. The FSM states call a
single method, EnsureTarget(), and this class decides whether the current target
is still valid and, if not, acquires a new one.

Centralising this is why PlayerIdleState is only five lines long.

INSPECTOR FIELDS
----------------
  Detection
    enemyDetectionLayer  (LayerMask) which layers count as enemies
    use2D                (bool, default true) use Physics2D.OverlapCircleAll
                         instead of the 3D Physics.OverlapSphere

  Retargeting
    respectFOV           (bool, default false) apply the FOV test when
                         validating or searching

    REMOVED 2026-09-17: allowNearestSwitch, onlySwitchIfInFront and
    retargetHysteresis. All three served one behaviour - "drop the enemy you
    have for a nearer one" - and that behaviour is now forbidden. Every other
    hero reads PlayerManager.currentTarget as a CLAIM, and a claim that can be
    dropped for 30cm of distance is not information anyone can act on.
    PlayerIdleState was the only caller and it passed `true`, so this was live
    code, not a dormant option.

KEY METHODS
-----------
  EnsureTarget(bool? overrideAllowNearestSwitch = null) -> bool
      The single entry point called from the states.

      RETURNS FALSE IMMEDIATELY WHILE playerManager.isUnlocked IS FALSE. A hero
      on its deploy gate picks nothing - same reason as rule 0 in
      PlayerManager.UpdateTargetSelection: locked heroes are invisible to
      TargetClaimRegistry, so a whole wave choosing while it waits on the gates
      all picks the same enemy. This is the SECOND acquisition path, so it needs
      the guard independently or it reopens the hole on its own.

      Otherwise ACQUIRE ONLY:
      if the current target is invalid, acquire the best enemy; if one is found,
      set playerManager.hasDetectedEnemyOnce = true (a latch other systems use to
      know the unit has engaged at least once). Returns whether a valid target
      exists afterwards.

      The parameter is KEPT SO PlayerIdleState STILL COMPILES and is no longer
      read. It is not an accidental no-op: "switch to whatever is nearest" is
      precisely the behaviour that sent two heroes at the same enemy while the
      other one walked into the player base.

  IsTargetValid(EnemyStats target, bool doFOV) -> bool
      not null, activeInHierarchy, NOT enemyIsdead, optionally inside the FOV.

      NO RADIUS TEST since 2026-09-17. It used to reject anything further away
      than detectionRadius, which contradicts the new rule: a hero is
      deliberately sent across the field to cover an enemy nobody else is on, and
      a radius test would declare that target invalid on arrival and re-acquire
      the nearest one - exactly the pile-up the rule removes.

      The enemyIsdead test is NEW. Only activeInHierarchy was checked before, so
      a corpse still playing its death animation read as a valid target and the
      hero stood waiting for it.

  AcquireBestEnemy(bool doFOV, EnemyStats exclude, out float bestDist)
      Runs an overlap query (2D or 3D depending on use2D) against
      enemyDetectionLayer within playerManager.detectionRadius, and returns the
      BEST valid EnemyStats: fewest other heroes handling it, then nearest, then
      lowest instance id. The ranking itself is TargetClaimRegistry.Beats, shared
      with PlayerManager.UpdateTargetSelection so the two acquisition paths in
      this project can never disagree about who to pick. Can exclude one
      candidate.

      Renamed from AcquireNearestEnemy - "nearest" stopped being the whole rule
      and a name that still said so would be a trap.

  AnyEnemyAliveInScene() -> bool
      Used by PlayerPursueTargetState to decide whether it is allowed to switch
      to attacking the enemy gate - units only go for the gate once no enemies
      remain.

  IsWithinFOV(Vector3 pos) / Distance2D3D(a, b)
      Helpers shared by the above, honouring the use2D flag.

HOW IT CONNECTS
---------------
  - PlayerIdleState, PlayerPursueTargetState and PlayerCombatState all rely on
    it instead of running their own physics queries.
  - Writes playerManager.currentTarget and hasDetectedEnemyOnce.
  - Calls TargetClaimRegistry.OtherClaimants / .Beats for the ranking.
  - This is the SECOND of two acquisition paths. The other is
    PlayerManager.UpdateTargetSelection, which runs every frame from Update and
    searches the whole field with no radius limit. They agree only because
    neither one may switch a living target - before stickiness, whichever ran
    last won.

NOTES
-----
  - REMOVED 2026-09-17: EnsureTarget1, a dead numbered variant with no call site.
    It differed only in not setting hasDetectedEnemyOnce, so reviving it would
    have left that latch false forever.
  - The overlap queries allocate an array on every call (OverlapCircleAll rather
    than the NonAlloc variant). Because they run per unit per state tick, using
    Physics2D.OverlapCircleNonAlloc with a reusable buffer would remove a
    meaningful amount of per-frame garbage when many units are alive.
  - respectFOV defaults to FALSE, so by default units will target enemies behind
    them. That is probably intentional for an auto-battler, but it means the FOV
    fields have no effect unless explicitly enabled.
