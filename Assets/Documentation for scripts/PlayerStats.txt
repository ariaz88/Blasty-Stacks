CURRENT UPDATE - 2026-09-16 (supersedes everything below about damage adjustment)
ApplyDamageToPlayer NO LONGER ADJUSTS DAMAGE AT ALL. CPBattleController.AdjustIncomingDamage and IsProtected are gone with the rest of the enforcement layer, so the blow lands exactly as the attacker's stats produced it. The order is now:
    damage = ClampIncomingBlow(damage, attacker)     loose safety guard only (maxHP/4)
    CPBattleController.ReportBlow(this, damage)      OBSERVATION ONLY, returns void
    SetResolvedHealth(...)
There is no winning-side mitigation and no champion HP safety net any longer - those decided the result in advance. `attacker` is still passed, now only so CharacterStats.ReportDeath can print the per-attacker hit breakdown.
The pause / battle-not-running gate that used to live inside AdjustIncomingDamage moved into CharacterStats.ClampIncomingBlow; it was the only thing enforcing it and this file never checked it independently.

--------------------------------------------------------------------------------
SUPERSEDED - 2026-09-10 (kept for history)
ApplyDamageToPlayer now passes real incoming hit damage through CPBattleController.AdjustIncomingDamage. No controller independently ticks HP. SetResolvedHealth is a health update helper only; it is called by ApplyDamageToPlayer, updates against live maxHealth, tolerates missing healthBar and flags death at zero. Stages 1-5 have explicit winning-side mitigation and a 1%-HP safety net; other stages keep normal damage.

================================================================================
  PlayerStats.cs
  Path : Assets/Scripts/Combat/Player/PlayerStats.cs
  Type : MonoBehaviour, extends CharacterStats
  Layer: Combat / Player
================================================================================

PURPOSE
-------
Holds a player unit's live health and handles incoming damage. Inherits the
shared health fields from CharacterStats.

FIELDS
------
  PlayerManager  cached in Awake via GetComponent
  healthBar      (HealthBar) the floating bar above the unit
  playerIsdead   (bool) set once HP reaches zero; polled by PlayerAttackState

LIFECYCLE
---------
  Awake()  caches the PlayerManager
  Start()  initialises the health bar from currentHP / maxHealth

METHODS
-------
  ApplyDamageToPlayer(float damageAmount)
      Subtracts damage, clamped so HP never goes below zero and a negative
      damage value cannot heal. Updates the health bar, and sets playerIsdead
      when HP hits zero.

HOW IT CONNECTS
---------------
  - EnemyDamageCollider calls ApplyDamageToPlayer on contact.
  - PlayerAttackState reads playerIsdead to route into PlayerDeathState.
  - PlayerManager reads and writes the inherited health fields.

NOTES
-----
  - INCONSISTENCY: Start() initialises the bar with maxHealth (from
    CharacterStats), but ApplyDamageToPlayer refreshes it with
    PlayerManager.statsBase.maxHP (the design-time SO value). If a roguelite
    skill raises max HP at runtime, those two denominators disagree and the bar
    will render at the wrong ratio after the first hit. Using the same source in
    both places would fix it.
  - Setting playerIsdead does not itself trigger the death state - PlayerManager
    or PlayerAttackState must notice it on a later tick.
