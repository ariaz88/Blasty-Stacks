PURPOSE
-------
Evaluates the CP weight curves at a given level and returns a plain struct of
numbers. Separating this from CPCalculator keeps the curve sampling in one place.

TYPES
-----
  struct Weights { wA, wH, wMv, wAS, wD, meleeMult, rangedMult }
      wR (range weight) was removed with A2 - range plays no part in CP.

METHODS
-------
  Evaluate(int level, CPWeightsConfigSO cfg) -> Weights
      Starts from hard-coded fallback defaults (wA=1, wH=0.15, wMv=0.25,
      wAS=0.40, wD=0, meleeMult=1, rangedMult=1.05) so that a null config still
      yields sensible weights.
      Otherwise samples every curve at 'level', clamps each by cfg.wClamp, and
      multiplies them all by globalWeightScaleByLevel (itself clamped to 1..10).
      The two flavour multipliers are sampled separately and do NOT get the
      globalWeightScale treatment - each is clamped to 1..5 on its own.

NOTES / BUGS
------------
  !! DEAD CODE AS OF THE A1 CP REWRITE. Nothing calls Evaluate() any more.
  !! CPCalculator used to be the sole caller; its new formula
  !! ((ATK x AtkSpd) x EffectiveHP / K) has no per-stat weights and no typeMult,
  !! so this class and CPWeightsConfigSO are both off the CP path. They are kept
  !! rather than deleted pending decision D4/E5 in
  !! Docs/cp-analysis/NEXT_VERSION_CHANGES.md.

  [FIXED 2026-09-08] meleeMult was never read from the config. The line that
  should sample cfg.meleeMultByLevel was missing, and rangedMult was assigned
  TWICE (the identical statement on two consecutive lines, 41-42), so
  meleeMult kept the hard-coded struct default of 1f and the meleeMultByLevel
  curve was completely ignored. Line 41 is now:
      w.meleeMult = Mathf.Clamp(cfg.meleeMultByLevel.Evaluate(L), 1, 5f);

  !! IMPORTANT: that fix changed NO CP value, and still does not. Verified
  !! against both config assets at every level 1..50:
  !!   - "Player CP.asset": meleeMultByLevel is authored OFF THE LEVEL AXIS
  !!     (keys at t = -389.47 and t = -357.95). Because AnimationCurve clamps
  !!     past its last key, Evaluate(L) returns 0.060408 for every L >= 1, and
  !!     the Clamp(..., 1, 5f) floor lifts that straight back to 1.0 - exactly
  !!     the value the buggy code already produced.
  !!   - "EnemyCP.asset": meleeMultByLevel is clean (flat 1.0 -> 1.0), so it
  !!     evaluated to 1.0 anyway.
  !! So the curve is now genuinely read, but it cannot influence anything until
  !! the Player CP curve is re-authored back onto the level axis (x = 1..50).
  !! Editing that curve in the Inspector today still appears to do nothing.

  !! The same off-axis fault affects rangedMultByLevel in "Player CP.asset"
  !! (keys at t = -729.95 / -694.19, evaluating to 0.026349). The Clamp floor
  !! of 1 rescues it to 1.0, hiding the fault. Both flavour curves in that asset
  !! need re-drawing before typeMult can do anything.

  - rangedMult is clamped to 1..5, and meleeMult now uses the same clamp, so a
    curve value below 1 is silently raised to 1. Neither class can be weighted
    BELOW 1.0, which means "this class is worth less per stat point" is not
    expressible. A band such as 0.5..2.0 would be more honest if the flavour
    system is ever made functional.

  - Note also that typeMult is currently a no-op for gameplay reasons beyond
    this file: every UnitStatsSO in the live roster (the 15 prefabs under
    Assets/PREFABS/Characters/New Characters/) is FighterType.Warrior, so
    CPCalculator's isRanged branch never executes and only meleeMult is ever
    read. See Docs/cp-analysis/CP_SYSTEM_ANALYSIS.md for the full trace.
