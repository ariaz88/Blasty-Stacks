PURPOSE
Campaign stages 1-5 only. "Level" in the design workbook means stage, not chapter.
Pure rules table - no MonoBehaviour, no runtime state. Everything the guaranteed-win
model needs to know about a stage lives here.

DEPLOYMENT
  Deployments   1: 1-1-1   2: 1-1-2   3: 1-1-2-1   4: 1-1-2-4   5: 1-1-2-2-2-4
  TotalPairs / HeroesForMatch / TotalHeroes read that table.
  FirstWinningMatch   levels 1-3 -> 1,  level 4 -> 3,  level 5 -> 4.
  ResolveLevel        reads the stage number out of the scene name ("..._Stage_N"),
                      else LevelConfig.levelNumber, else LevelManager.CurrentStage.

COMBAT POWER
  PerHeroCP(level)    100 at level 1, 125 at levels 2-5. This is the reference for
                      ONE hero; CPBattleController normalises the team TOTAL to
                      heroCount x this. Heroes are NOT flattened individually any
                      more - see NOTES.

  EnemyUnitCPs(level) Per-enemy CP in spawn order, where the design authored
                      individual values instead of a team budget:
                          level 1    35
                          level 2    35, 35
                          level 3    35, 40, 40      (level 3 adds a second type)
                          level 4-5  null -> team budget
  ReferenceEnemyCP    Sum of the per-unit list where one exists, so the two can
                      never drift apart; 400 / 650 for levels 4-5.

THE DAMAGE BUDGET
  DamageBudgetPerEnemy(E)
      How much of the PROTECTED hero's maximum HP a single enemy may ever remove:
          (100 / E) - 5, rounded UP to the nearest 5
      E=1 95%    E=2 45%    E=3 30%    E=4 20%    E=5 15%
      Sized so E enemies together always leave the hero standing, even if every
      ally falls and it ends up facing the whole army alone.

  MinHitsToSpendBudget = 4
      An enemy needs at least four hits to spend its allowance, so no single blow
      takes a visible chunk. At E=3 that is 30% / 4 = 7.5% per hit.

MINIMUM HITS TO KILL - every stage, level is irrelevant
  MinHitsToKillAnyone = 8
  MaxHitsToKillAnyone = 11
  DefenseForMaxHits   = 80
  HitsToKill(defense) -> blows this defender takes, interpolated across the band

      Nobody - hero or enemy, any level - dies in fewer than 8 blows, and no duel
      runs past about 11. Each blow lands between 9.1% and 12.5% of the target's
      maximum. Where a unit sits is decided by its own DEFENCE, so a tougher
      character genuinely takes 9, 10 or 11, and an upgrade walks it up the band.

      Measured on the live roster: defence 10 -> 8 hits, 25 -> 9, 40 -> 10,
      52 -> 10, 65 -> 10, 78 -> 11.

  (superseded) MinHitsToKillAnyone = 4
      Nobody dies in fewer than four hits, hero or enemy, at any stage 1-5.
      Enforced in CharacterStats.ClampIncomingBlow (NOT in CPBattleController -
      it was there first and did not hold; see that file's notes) as a CEILING of
      maxHP/4 on each blow, never a floor - that is the whole point. A blow already gentler than a quarter passes untouched, so a
      high-defence unit still takes its natural 5, 6, 7 or 8.

      Measured on the live roster (both directions, 240 pairings per level):
        level 4   4 hits x146   5 x52   6 x26   7 x13   8 x3
        level 5   4 hits x148   5 x49   6 x32   7 x10   8 x1
      Roughly 40% of matchups run longer than the floor, driven by the real
      defence spread (heroes 10..80, enemies 25..78).

      WHY A DAMAGE CEILING AND NOT AN HP INCREASE: maxHP is a CP INPUT
      (CP = ATK x AtkSpd x HP x (1 + DEF/100) / 200). Raising HP to stretch a
      fight raises that unit's CP, which moves the Player/Enemy CP ratio, which
      changes the result the workbook says the match must produce. The ceiling
      buys identical pacing and leaves every CP figure untouched.

TUTORIAL PRESENTATION - levels 1-3 only
  These three levels are an explicit exception. They are guaranteed wins fought by
  one or very few heroes, and at those CP ratios REAL combat reads badly: a level 1
  hero at CP 100 against a CP 35 enemy deletes it in a single blow. So the exchange
  is scripted for appearance, while levels 4-5 keep real combat.

  IsTutorialPresentation(level)   true for 1, 2, 3
  TutorialHitsToKillEnemy  = 4    each blow removes exactly a quarter of the enemy
                                  and the kill lands on the fourth swing
  TutorialHeroDamagePerHit = 0.07 every enemy blow removes a flat 7% of a hero's
                                  maximum - set in BOTH directions, not capped
  TutorialEnemySpeedScale  = 0.6  enemies walk 40% slower in these levels, so the
                                  last one cannot stroll past the fight and reach
                                  the player's base while the hero is still busy

  REMOVED: "SoloRushHitsToKill = 2" (2026-09-11). It let a lone, outnumbered hero
  kill in two, which only ever applied to levels 2 and 3 - exactly the levels the
  tutorial script now covers at four. The pressure it relieved is handled instead
  by the speed reduction, which looks far better than deleting enemies in two hits.

HOW IT CONNECTS
  - CPBattleController    reads every value above
  - EnemySpawner          ResolveLevel, AppliesTo, enemy counts
  - PlayerWaveManager     deployment sequence and RuleLevel
  - CPCalculator          AppliesTo gates which rounding path CP display uses

NOTES
  - Stage 6+ is out of scope entirely: AppliesTo returns false and every caller
    falls back to the original behaviour.
  - The workbook's win/loss column is reproducible from the CP ratio alone
    (R = PlayerCP / EnemyCP): R<0.75 Fast Loss, <1.00 Slow Loss, <1.15 Normal Win,
    else Fast Win. Verified against all 51 rows of levels 1-10 with zero mismatches.
    FirstWinningMatch is therefore just "the first match where R crosses 1.00",
    kept as an explicit table only because CPBattleController asserts the two agree.
  - Enemy CP for levels 1 and 2 is deliberately BELOW the workbook totals (35 and
    70 against 80 and 100). Arash set the per-unit values directly on 2026-09-11;
    the recorded outcomes are unchanged because both were already clear wins.
  - The per-unit list is indexed by SPAWN ORDER, not by enemy type, so it stays
    deterministic regardless of how EnemySpawner.ReferenceEntries cycles the
    authored prefabs. Editing a row re-balances that stage and nothing else.
