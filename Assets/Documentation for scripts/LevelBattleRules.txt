CURRENT UPDATE - 2026-09-16  EVERY CP TARGET AND OUTCOME RULE REMOVED
Deleted (Arash, 2026-09-16), and not to be reintroduced as constants:
    PerHeroCP, EnemyUnits / EnemyUnitCPs, ReferenceEnemyCP, FirstWinningMatch,
    DamageBudgetPerEnemy, MinHitsToSpendBudget, FlankedDamageScale,
    FlankEngageRange, SurroundedEnemyCount, SurroundedDamagePerHit,
    IsTutorialPresentation, TutorialHitsToKillEnemy, TutorialHeroDamagePerHit,
    MaxHitsToKillAnyone, DefenseForMaxHits, HitsToKill(defence),
    MinHitsToKillAnyone (renamed - see below)

`MinHitsToKillAnyone` is now `BaseStateBlowsToKill = 8`, and the rename is the
point: it is an AUTHORING target for level-1 stats, not a rule anything enforces at
runtime. See BASE-STATE CALIBRATION below.

They described CP the wrong way round. CP is BOTTOM-UP: a unit's CP comes from that
unit's own stats, and a side's total is the plain SUM of its units. A per-level CP
TARGET can only be met by writing stats back into units - which is exactly what
erased the player's upgrades. Enemy strength now comes from each type's own
ProgressionConfigSO growth curve; hero strength from the player's upgrades.

The workbook figures those tables encoded (Wittle_Defender_Levels_6-10_Balance.xlsx)
are now a VALIDATION TARGET, not an input: author base stats and curves, sum the CP,
compare, adjust. Landing near the figures is the goal; matching them exactly is not.

--------------------------------------------------------------------------------
PURPOSE
Authored per-stage pacing tables. "Level" in the design workbook means STAGE, not
chapter. Pure rules table - no MonoBehaviour, no runtime state.

What remains shapes only a battle's SIZE and LENGTH. Nothing here knows which side
is supposed to win, and nothing in this file may grow back into a rule that does.

Coverage is deliberately split:
    Deployments / AppliesTo     stages 1-5
    EnemyWaves                  stages 1-10
    hits-to-die band            every stage

DEPLOYMENT
  Deployments   1: 1-1-1   2: 1-1-2   3: 1-1-2-1   4: 1-1-2-4   5: 1-1-2-2-2-4
  TotalPairs / HeroesForMatch / TotalHeroes read that table.
  ResolveLevel  reads the stage number out of the scene name ("..._Stage_N"), else
                LevelConfig.levelNumber, else LevelManager.CurrentStage.

ENEMY WAVE COUNTS - levels 1-10  (Arash, 2026-09-14)
    L1 [1]    L2 [2]    L3 [3]
    L4 [2,3]  L5 [2,3]                    5 each, but in TWO waves, not one clump
    L6 [3,3]  L7 [3,3]                    6 each
    L8 [3,4]  L9 [3,4]  L10 [3,4]         7 each

  EnemyWaveCounts(level) -> int[] per wave in spawn order, or null past level 10
  TotalEnemies(level)    -> sum across waves, 0 when unauthored
  MaxAuthoredEnemyLevel  -> 10

  Levels 4+ MUST arrive in two or more waves - that is the point of the table, not
  the totals. EnemySpawner.BuildWavesFromRules consumes it.

  COUNTS ONLY. This table says how many enemies arrive and when; it says nothing
  about how strong they are. Total enemy CP is whatever the spawned units sum to.

  Levels 11+ are unauthored: the LevelConfig asset's own waves are used verbatim, so
  counts stop growing there while stats keep rising. Extending this table, or
  replacing it with a curve, is open work.

BASE-STATE CALIBRATION - an AUTHORING target, not a runtime rule
  BaseStateBlowsToKill = 8      <- the only constant left here
  (the loose runtime guard is CharacterStats.SafetyBlowFloor = 4)

  WHAT IT MEANS. At the BASE state - stage 1, nothing upgraded - a character should
  take about eight blows to die. Author each unit's level-1 maxHP to land there
  against its level-1 opponent:

      maxHP  such that  EffectiveHP / ATK_opponent  ~= 8
                        (EffectiveHP = maxHP x (1 + DEF/100))

  WHAT IT DOES NOT MEAN. It is NOT "nobody may ever die in under eight blows".
  The count is SUPPOSED to drift, and the drift is the difficulty signal:

      enemies grow EVERY stage; the player upgrades only every ~5 stages
          stage 1  ~8 blows to kill the hero
          stage 3  ~7
          stage 4  ~5     <- "you are under-levelled, go upgrade"
          stage 5  upgrade raises ATK *and* HP together, back to ~8

  A hard eight-blow floor used to sit in CharacterStats and it ERASED that signal:
  an under-levelled hero still survived its full eight blows, so the player never
  felt behind. It also silently protected whoever was losing. Removed 2026-09-16.

  REMOVED, in two steps, and not to come back:
    1. MaxHitsToKillAnyone (11), DefenseForMaxHits (80), HitsToKill(defence) and the
       maxHP/11 damage FLOOR. The floor lifted every weak blow to the same value, so
       a feeble attacker and a strong one landed IDENTICAL damage - ATK stopped
       affecting who wins and CP could only predict through attack speed. Scaling
       hits-to-die by defence also double-counted defence, which already reduces
       every blow in CombatMath.DamagePerHit.
    2. The maxHP/8 damage CEILING that guaranteed the eight blows. Eight belongs to
       the base state, not to the whole campaign.

  Measured after both removals, 1000 HP defender, guard maxHP/4 = 250:
      raw 600 -> 4 blows (guard bit)   raw 143 ->  7      raw 91 -> 11
      raw 250 -> 4 blows               raw 125 ->  8      raw 71 -> 15
      raw 200 -> 5 blows               raw 111 -> 10      raw 50 -> 20
  5, 6 and 7 blows are now reachable - impossible under the old clamp.

SIZING THE TWO GROWTH RATES
  Enemy growth per stage `g`, hero upgrade factor `U` every `N` stages:

      U ~= g^N          (N = 5 as a working assumption)

  so each cycle returns to roughly the same place. Whether the enemy finishes a cycle
  slightly ahead of the hero or slightly behind is a DESIGN choice to be taken from
  the balance workbook - Arash will set the actual figures. Until then, nothing in
  code assumes either.

THE PLAYER'S BASE
  BaseChipPerBlow = 0.01
      What one connected blow takes off the PLAYER's base WHILE THAT BASE STILL HAS
      LIVING DEFENDERS - 1% of maximum, a hundred blows to fell it. Once every hero
      has fallen the base takes full damage and the stage ends.

      GATED ON WHETHER DEFENDERS ARE ALIVE, not on any intended outcome. It briefly
      keyed off CPBattleController.BattleIsAnExpectedWin, damping the base only in
      battles a script had already decided the player would win; that question no
      longer exists. Taking literally NOTHING read as a broken game, which is why it
      chips rather than being immune.

      The ENEMY gate is NOT chipped - it keeps full immunity while its own defenders
      live (CPBattleController.HasLivingDefenders), because felling that gate ENDS
      the stage in a win and a stray hero should not finish a battle its army is
      losing.

HOW IT CONNECTS
  - EnemySpawner          ResolveLevel, AppliesTo, EnemyWaveCounts
  - PlayerWaveManager     deployment sequence and RuleLevel
  - CharacterStats        BaseStateBlowsToKill (reported only; the runtime guard is
                          CharacterStats.SafetyBlowFloor, which lives there not here)
  - PlayerGateStats       BaseChipPerBlow
  - CPCalculator          AppliesTo gates which rounding path CP display uses

NOTES
  - THE R BANDS ARE STILL THE BEST DESCRIPTION OF THE WORKBOOK, and they are now a
    PREDICTION to be measured rather than a rule to be enforced:
        R < 0.75  Fast Loss     R < 1.00  Slow Loss
        R < 1.15  Normal Win    else      Fast Win
    Verified against all 51 rows of levels 1-10 with zero mismatches. Feed
    CPCombatVerification's recorded rows back against these to see how well real
    combat reproduces them.
  - The workbook's Enemy CP column disagreed with the old code for levels 1-2
    (80/100 vs 35/70). Both tables are gone, so the conflict is moot - but expect
    early-stage totals to differ from the workbook until base stats are retuned.
  - AppliesTo is still 1-5 while EnemyWaves spans 1-10. Widening AppliesTo needs
    Deployments rows for 6-10 first.
  - Enemy growth currently compounds to roughly +22% CP per stage (atk 8% x hp 10% x
    atkSpd 2% in ProgressionConfigSO), about 44x by stage 20. That is far too steep
    for an upgrade cadence of a few stages and is the next thing to retune - open
    work, not done here.
