0. THE BIG PICTURE - WHAT THE USER IS CHANGING
----------------------------------------------
The game used to run the puzzle and the combat at the same time: the level
loaded, EnemySpawner immediately started sending waves, and every puzzle match
threw a group of heroes off the gate into the field.

The user is replacing that with a PUZZLE-FIRST flow:

  1. The stage opens showing only the board + the player gate. No enemies.
  2. The player rearranges pieces on the board, limited to N moves.
  3. Nothing enters combat until the player presses the BATTLE button.
  4. Only then does the enemy spawner start.

New screen layout, bottom to top:
  - Ads banner strip (very bottom)
  - Feature Panel (hammer / refresh / potion / BATTLE button with energy cost)
  - Puzzle board
  - Player gate (with the 1000 HP bar)
  - Battlefield area (top)

The ENEMY GATE is no longer visible on screen - the user disabled EnemyCastle
in the scene.

2. WHAT WAS ACTUALLY IMPLEMENTED (3 changes)
--------------------------------------------

CHANGE 1 - Enemy spawner gated behind the BATTLE button
  EnemySpawner got a "waitForBattleStart" checkbox. When ON, the spawner does
  nothing at level load; a new public StartBattle() is the only way to begin.
  It is idempotent, so double-clicking BATTLE cannot start two wave loops.
  The flag DEFAULTS TO OFF, which is deliberate: Level_1_Stage_1..20 were
  authored before the field existed, so they deserialize it as false and keep
  their original auto-start behaviour. Only the new scene ticks it ON.

  A new component BattleStartController drives the BATTLE button: it charges
  the allowance (below), then calls EnemySpawner.StartBattle().

CHANGE 2 - 25 battles per 24 hours (global)
  New static service BattleEnergyService. Rules:
    - 25 free battles inside a ROLLING 24h window.
    - The window opens on the FIRST battle, not at midnight, so it does not
      depend on the device timezone.
    - The allowance is GLOBAL - shared by every stage, not per scene. Reloading
      a stage does not refund a battle.
    - Past the free 25, a battle costs ENERGY.

  ENERGY IS A PLACEHOLDER, as the user requested. Nothing grants energy yet, so
  in practice the player is blocked until the window resets. When the real
  economy is written it only needs to call AddEnergy(); nothing else changes.

  TEST MODE (currently ON): BattleStartController has a
  "doNotPersistAllowance" flag, default ON, which puts the allowance in memory
  only so every Play session starts with a full 25 and NOTHING is written to
  the save file. THIS MUST BE TURNED OFF FOR RELEASE.

  Why that flag exists: GameStartManager wipes the whole save on every run
  (its Awake hardcodes resetBool = true), but GameStartManager is NOT in the
  gameplay scenes - it arrives via DontDestroyOnLoad from StarterScene. So
  pressing Play directly on a stage would otherwise persist the count.

CHANGE 3 - Move budget on the board
  New component PuzzleMoveBudget with a "movesAllowed" number (0 = unlimited).
  Reference image: "BATTLE BEGINS IN 8 MOVES".

  DEFINITION OF A MOVE (exactly as the user specified):
    A move counts ONLY when a piece is picked up and dropped on a DIFFERENT
    cell. Tapping a piece and releasing it where it already sat does NOT count.
    A drag the board refused does NOT count either, because the piece slides
    back and the anchor is unchanged.
    BoardInputController implements this by remembering the anchor at pickup
    and comparing it at release.

  When the budget is spent the board stops accepting NEW pickups (an in-flight
  drag still finishes). Running out of moves does NOT auto-start the battle -
  the player still has to press BATTLE.

  IMPORTANT DESIGN DECISION: the budget lives on the SCENE, not on LevelConfig.
  There are only TWO LevelConfig assets (Spawner1.asset / Spawner2.asset) and
  they are shared by all 20 stage scenes, so a value there would not be
  per-level. Each stage IS its own scene, so the scene is the correct per-level
  home. If a real per-stage config table is ever built, that field is the one
  place to re-source.


3. ADMOB BANNER - WHAT WAS INSTALLED AND CONFIGURED
---------------------------------------------------
The project already had a well-written AdManager facade, but the SDK was never
installed, so every AdMob call sat behind a GOOGLE_MOBILE_ADS define that was
never set - meaning ShowBanner() did literally nothing.

Installed and configured:
  - Added com.google.ads.mobile (v11.2.0) and
    com.google.external-dependency-manager (v1.2.187) to Packages/manifest.json.
    BOTH ARE GIT URLS. EDM4U is normally taken from Google's scoped registry
    (unityregistry-pa.googleapis.com) but that registry was UNREACHABLE from
    this machine and resolution failed. The git url is the working equivalent.
    If the scoped registry is ever restored, drop the git url for EDM4U at the
    same time - do not keep both.
  - Set the GOOGLE_MOBILE_ADS scripting define for Android, iOS AND Standalone.
    Standalone was included on purpose: the editor's active build target is
    StandaloneWindows64, so without it the whole ad code path stays compiled
    out and cannot be tested at all.
  - Created Assets/GoogleMobileAds/Resources/GoogleMobileAdsSettings.asset and
    filled in Google's TEST app ids. An Android build with an empty app id
    CRASHES ON STARTUP, which is why they are set even in development.
  - link.xml is NOT needed - the package ships its own.

Upgraded the banner in AdManager:
  - It now uses an ANCHORED ADAPTIVE banner (full device width, SDK-chosen
    height) instead of the legacy fixed 320x50, plus load/fail events, retry by
    rebuilding the view, and a BannerHeightPixels property.

New component AdBannerSlot, placed on "Ads Banner panel":
  - The AdMob banner is a NATIVE OVERLAY. The SDK draws it on top of the Unity
    view; it is not a Unity UI element and it pushes nothing out of the way.
    Without a reserved strip it simply COVERS the Feature Panel and the BATTLE
    button. Reserving that strip is this component's whole job.
  - It requests the banner while its scene is active and resizes the strip to
    the real banner height once it loads.
  - NOTHING SHOWS IN THE EDITOR GAME VIEW - the native overlay does not exist
    there. The placeholder text stands in for it. This is expected, and the
    user already knew it.

AdManager placement: the user asked for it in Assets/Scenes/StarterScene.unity,
which is the boot scene (it already holds GameStartManager, CurrencyManager and
MenuLoader). It survives into gameplay via DontDestroyOnLoad.


4. TWO BUGS FOUND AND FIXED ALONG THE WAY
-----------------------------------------
BUG A - SaveSystem migration recursion (PRE-EXISTING, not introduced here)
  LoadInternal() called Save() during its version migration, but Save() reads
  the Data property and the cache was still null at that moment, so Data called
  LoadInternal() again. The saveDepth > 10 guard stopped the stack overflow,
  but the migration then NEVER PERSISTED - so it re-ran and logged
  "[SaveSystem] Recursion guard: Skipping save" on EVERY launch.
  Fixed by publishing the cache immediately before saving. Those two lines must
  not be reordered. The save file is now correctly at version 2.
  The doc file had already flagged this as a known latent bug; it is now marked
  fixed.

BUG B - AdBannerSlot resized a stretched RectTransform wrongly (self-inflicted,
  caught before it shipped)
  "Ads Banner panel" uses STRETCH anchors (0,0 -> 1,1) with sizeDelta.y of
  -2302.38, giving a real height of 133.62 canvas units. On a stretched rect,
  sizeDelta.y is an OFFSET FROM THE PARENT'S HEIGHT, not an absolute height, so
  writing a height into it would have blown the layout apart. Now it uses
  SetSizeWithCurrentAnchors, which is correct under any anchor setup.

  - SESSIONS.md is the cross-session log; read it first, append at the end.
