PURPOSE
-------
A TEMPORARY debug gate sitting in front of ALL disk persistence. Added on
2026-09-20 so that every Play run starts as a brand-new player: stage 1, zero
coins / gems / hero XP, default roster. Before this, commit c94a908 removed the
old hard-coded boot wipe (GameStartManager used to run resetBool = true ->
OnResetButtonClicked() in Awake), which made saves persist for the first time -
so pressing Play resumed at whatever stage had last been reached (stage 6 with
banked resources) instead of starting clean.

This class does NOT delete anything. It only decides whether reads and writes
are allowed. Turning it back on resumes normal save/load behaviour.

CONSTANTS / FIELDS
------------------
  ToggleKey  (private const string) = "DEBUG_SAVE_PERSISTENCE_ENABLED"
      Its own PlayerPrefs key, deliberately separate from "GAME_SAVE_V1" so
      SaveSystem.ResetAll() (which deletes only GAME_SAVE_V1) can never clear
      the toggle itself.
  FreshStartCoins / FreshStartGems / FreshStartHeroXp  (public const int) = 0
      What a non-persisted session seeds its wallet with. These deliberately
      BYPASS CurrencyManager's inspector values (startingGems 4, startingCoins
      4, startingHeroXP 6 in StarterScene.unity), which would otherwise hand the
      player resources on a "fresh" run.
  _cached  (private static int, -1 = not read yet)
      PlayerPrefs read-through cache. Save() runs on nearly every state change,
      so the gate is checked extremely often; this keeps it off PlayerPrefs.

MEMBERS
-------
  Enabled  (public static bool)
      GET: false by default (PlayerPrefs.GetInt(ToggleKey, 0)) - the gate ships
           DISABLED, which is the whole point of the change.
      SET: early-outs if unchanged; otherwise writes + flushes PlayerPrefs.
           When switching to TRUE it immediately commits the session's current
           state via SaveSystem.Save() and LevelManager.PersistCurrentStage(),
           so enabling mid-session captures progress right away instead of
           waiting for the next incidental state change.
  Toggle()  (public static void)
      Enabled = !Enabled.

COMPILATION GATING
------------------
The real implementation is wrapped in
    #if UNITY_EDITOR || DEVELOPMENT_BUILD
In a non-development player the #else branch hard-wires
    Enabled => true   (setter is a no-op)
    Toggle() => no-op
so shipping a release build while the editor toggle is off CANNOT disable saving
for real players. This is the main safety property of the design.

WHAT CHANGES WHEN Enabled == false
----------------------------------
  SaveSystem.Save()        still stamps savedAtUtc and still mutates the
                           in-memory cache, but returns before touching
                           PlayerPrefs. The running session therefore behaves
                           completely normally - progress is live, just volatile.
  SaveSystem.LoadInternal() returns a brand-new SaveData(), ignoring any
                           existing GAME_SAVE_V1 blob on disk.
  LevelManager.Awake()     ignores "LM.CurrentStage" and boots at startingStage.
  LevelManager
    .PersistCurrentStage() no-ops, so a stage change can't leak to disk.
  GameStartManager
    .InitializeServices()  seeds the wallet from FreshStart* (0/0/0) instead of
                           CurrencyManager.Starting*.
  SaveSystem
    .ResetAllIfRequested() zeroes runtime currency instead of restoring the
                           CurrencyManager starting values, so a mid-session
                           reset matches what a relaunch would produce.

HOW IT CONNECTS
---------------
  - SaveSystem            - Save() and LoadInternal() both consult it.
  - LevelManager          - Awake(), PersistCurrentStage(), ResetProgressToStart().
  - GameStartManager      - first-run economy seeding.
  - SavePersistenceDebugPanel  - the in-game on-screen toggle button.
  - SavePersistenceMenu   - the Editor "Tools/Save System" menu equivalent.
  - EarlyCampaignVerification  - forces the gate ON for the duration of a run
                          (snapshotting and restoring the previous value the
                          same way it already does for DirectPlayMenu.Enabled),
                          because that harness drives scenarios through saves
                          that must survive a play-mode transition.

NOTES
-----
  - THE GATE DOES NOT ERASE AN EXISTING SAVE. A save written before it was
    introduced is still sitting in PlayerPrefs; it is merely ignored. To
    actually clear it, use Tools > Save System > Wipe Saved Progress Now (see
    SavePersistenceMenu), or the "Reset progress now" button on the debug panel.
  - Persistence in this project funnels through exactly two PlayerPrefs keys:
    "GAME_SAVE_V1" (SaveSystem: units, currency, stars, tutorials, deploy
    stages, battle energy) and "LM.CurrentStage" (LevelManager). Both are gated
    here. Any NEW direct PlayerPrefs write added elsewhere would escape the gate
    - route new save data through SaveSystem, per the project convention.
  - This is intended to be TEMPORARY. When the balance pass no longer needs a
    clean boot every run, flip the gate on (or delete this class and its two
    UI entry points and inline `true` at the five call sites).
  - The toggle is remembered between sessions, so it only has to be flipped once.
