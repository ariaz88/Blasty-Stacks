CURRENT UPDATE - 2026-09-16  THE ENFORCEMENT IS GONE; THIS IS NOW A READ-ONLY REPORTER
This script used to decide the winner before the battle began. All of that was
removed (Arash, 2026-09-16). What is left only MEASURES.

Removed, and none of it may come back:
  * the hero rescale to heroCount x PerHeroCP - it ERASED the player's Units-menu
    upgrades at battle start, which was the reported bug;
  * PlayerShouldWin (from MatchesCleared) and the throw when CP disagreed with it;
  * ChooseChampion + LimitDamageToChampion - one hero that could not lose, and a
    per-enemy lifetime damage allowance against it;
  * ScriptTutorialBlow / IsTutorialExchange - levels 1-3 staged outright;
  * CountEngagedFlankers / ChampionIsFlanked / ChampionIsSurrounded - they existed
    only to feed the champion's damage budget;
  * ScaleToCP / ApplyFactor / EnemyScale - top-down distribution of a team CP
    budget across the enemies;
  * BattleIsAnExpectedWin - the player's base damped only in battles the script had
    already decided the player would win;
  * CalibrateHero's normalisation half (the MeleeContactRecovery half survives as
    RegisterHero).

If a future change needs one side to win, change its STATS or its growth curve.
Never this file.

--------------------------------------------------------------------------------
PURPOSE
Read-only combat-power reporter, added at runtime by EnemySpawner for EVERY battle
at every stage. It keeps the roster of both sides, sums their CP and reports the
ratio. It never writes to a unit, never adjusts damage, and never ends a battle.

CP IS BOTTOM-UP
  CP_unit  = ATK x AtkSpd x maxHP x (1 + DEF/100) / 200     (CPCalculator.UnitPower)
  PlayerCP = sum of CP over the heroes on the field
  EnemyCP  = sum of CP over the enemies on the field
  Ratio    = PlayerCP / EnemyCP

Totals are READOUTS, never inputs. Same enemy type -> same stats -> same CP;
different type -> different base -> different CP. A hero fights with exactly the
stats the player's upgrades produced; an enemy with exactly the stats its type's
ProgressionConfigSO curve produced.

FIELDS
  Instance / IsPrepared        scene-scoped singleton and readiness flag
  Level                        global stage number, for the report line
  PlayerCP / EnemyCP / Ratio   summed live on read, never cached, never written back
  HeroCount / EnemyCount       roster sizes
  HeroDeaths / EnemyDeaths / FewestHitsBeforeDeath
                               telemetry read by CPCombatVerification
  playerCurve / enemyCurve     RESERVED, unused. Arash asked for a per-side curve to
                               be available here. Nothing reads them, and nothing may
                               read them to CHANGE a unit - reporting or prediction
                               weighting only.
  heroUnits / enemyUnits       the managers, for CP
  heroes / enemies             their CharacterStats, for HasLivingDefenders

FLOW
  Prepare(spawner, waves)
    Snapshots whichever heroes are already on the field, sets IsPrepared, logs the
    opening report. DELIBERATELY CANNOT FAIL and returns void: heroes now arrive
    progressively through HeroDeploymentSequencer's timed loads, so an empty roster
    at battle start is the NORMAL case, not an error.
    The old Prepare returned bool and aborted the spawn coroutine on an empty
    roster, which is why it had to be gated off entirely under the card-reward flow -
    with it enabled, not one enemy ever spawned.

  RegisterHero(hero)                                                    [static]
    Ensures MeleeContactRecovery, then adds the hero to the CP roster.
    CALLED FOR EVERY HERO AT EVERY STAGE. It used to be CalibrateHero, gated on
    UsesDeploymentRules AND bailing out again inside for any level outside 1-5, so
    heroes from stage 6 on never got the melee unstick helper at all.

  RegisterEnemy(enemy)
    Ensures MeleeContactRecovery, then adds the enemy to the CP roster. Its stats
    are NOT touched - they come from EnemyManager.RebuildFromBase.

  HasLivingDefenders(gate)                                              [static]
    TRUE while the gate's own side still has living defenders.
    KEPT, and it is NOT outcome forcing: it never asks who should win and applies
    identically whatever the CP figures say. It encodes one structural rule - you
    must defeat the defending army before you can fell the castle - so a single fast
    unit cannot walk past a live battle and end the match alone. Without it the
    winner would often be whoever ran past first, which would make CP LESS
    predictive, not more.

  LogEveryBlow  [static bool, default TRUE]  +  TotalBlowsThisBattle
    Every landed blow prints one line:
        [BLOW #7] Player_CowMinotaur_02(Clone) -> Enemy_Reaper_Man_01(Clone) (ENEMY)
        dmg 55.4   HP 117.1 -> 61.7 / 394   this target has now taken 7 blow(s)
    and the killing blow appends "*** DEAD after N blow(s) ***".
    #n is the running total for the WHOLE battle; "this target has now taken N" is
    the per-victim count, which is the number that answers "how many hits to kill".
    ADDED 2026-09-16 because counting on screen and counting in code disagreed:
    watching counts ANIMATION SWINGS, including those that never connect, while only
    landed blows reach here. Set LogEveryBlow=false to silence it once tuned.

  ReportBlow(target, damage, attacker)                                  [static]
    Purely observational: returns nothing, changes nothing. Called by
    PlayerStats/EnemyStats AFTER the damage is final, so the telemetry describes
    what really happened. Counts hits per victim and records deaths.

HOW IT CONNECTS
  - EnemySpawner             creates it, calls Prepare, then RegisterEnemy per spawn
  - PlayerWaveManager        calls RegisterHero for every hero it spawns
  - PlayerStats/EnemyStats   call ReportBlow after ClampIncomingBlow
  - PlayerGateStats          chips while HasLivingDefenders is true
  - EnemyGateStats           fully immune while HasLivingDefenders is true
  - CPCombatVerification     reads PlayerCP / EnemyCP / Ratio and the telemetry

NOTES
  - THE MINIMUM-BLOWS RULE IS NOT HERE and is not enforcement. It constrains how
    LONG a fight lasts, not who wins it, and lives in
    CharacterStats.ClampIncomingBlow where no early return can skip it. It is a
    FLOOR of eight blows with NO matching ceiling (Arash, 2026-09-16) - a weak
    attacker takes as many swings as its stats say, unbounded.
  - THE PAUSE GATE MOVED OUT. "no damage while paused or before the battle runs"
    used to sit inside AdjustIncomingDamage and was the ONLY thing enforcing it -
    PlayerStats and EnemyStats never checked it themselves. It is now the first line
    of CharacterStats.ClampIncomingBlow. Do not drop it.
  - LevelGameManager no longer skips mutual-wipe auto-defeat while IsPrepared. That
    check existed because scripted stages required a physically destroyed gate; with
    the reporter prepared for every battle it would have disabled stalemate
    detection permanently and hung the stage in Playing forever.
  - WHY THE OLD MODEL EXISTED AT ALL: heroes vastly outnumbered enemies (12 v 5 at
    level 5). Melee advantage is superlinear in unit count, so those fights ended
    instantly and had to be staged to look like fights. The real fix is the counts
    and the stats, not a script. Bringing the two sides closer together is open work.
