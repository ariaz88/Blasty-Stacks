CURRENT UPDATE - 2026-09-16 (supersedes the gate-damping notes below)
ApplyDamageToPlayerGate now CHIPS while the base still has living defenders, at EVERY stage:
    CPBattleController.HasLivingDefenders(this) -> damage = maxHealth * LevelBattleRules.BaseChipPerBlow (1%)
    no living defenders                         -> full weapon damage, and the stage ends
This replaces the gate on CPBattleController.BattleIsAnExpectedWin, which damped the base only in battles a script had already decided the player would win. That question no longer exists - the battle decides its own result - so the rule is now outcome-neutral: an attacker that slips past a LIVE battle must not decide the match on its own, mirroring the enemy gate.
Chipping rather than full immunity is deliberate: taking literally nothing read as a broken game, and a hundred connected blows to fell a defended base settles nothing.

SUPERSEDED - 2026-09-10 (kept for history)
Stages 1-5 reject incoming hits while the gate's own registered defending heroes are alive. After defenders are defeated, ordinary weapon damage reduces gate HP and its existing destruction event ends the stage. No controller damages or destroys this gate. UI references are null-safe. Stages 6+ have no new gate protection.

================================================================================
  PlayerGateStats.cs
  Path : Assets/Scripts/Combat/Player/PlayerGateStats.cs
  Type : MonoBehaviour, extends CharacterStats
  Layer: Combat / Player
  Scenes: all 7 gameplay stages
================================================================================

PURPOSE
-------
The player's BASE / castle. Its destruction is the LOSE condition of a stage.
It tracks health, shows a health bar and a numeric label, and broadcasts a
static event when it falls.

THE KEY EVENT
-------------
  public static event Action OnGateDestroyed;
      A static event, so LevelGameManager can subscribe without any scene
      wiring. This is the clean event seam between gameplay and game-flow.

FIELDS
------
  playerManager        cached in Awake
  healthBar            (HealthBar) the visual bar
  isPlayerGateDestroyed (bool) latch preventing double-destruction
  baseTxt              (TextMeshProUGUI) numeric HP label on the gate

LIFECYCLE
---------
  Awake()  caches the PlayerManager
  Start()  initialises the health bar (null-checked) and writes currentHP into
           baseTxt

METHODS
-------
  ApplyDamageToPlayerGate(float damageAmount)
      Returns immediately if already destroyed. Subtracts damage clamped so HP
      cannot go below 0 and negative damage cannot heal. Updates the label
      (floored to an int) and the bar. At zero HP calls DestroyGate().

  DestroyGate()  [private]
      Guarded by isPlayerGateDestroyed so it can only fire once, then raises
      OnGateDestroyed.

  DeactivateGate()  [coroutine]
      Waits 0.5s then deactivates the GameObject. NOTE: it is defined but never
      started - the gate currently stays visible after destruction.

HOW IT CONNECTS
---------------
  - EnemyDamageCollider calls ApplyDamageToPlayerGate.
  - LevelGameManager subscribes to OnGateDestroyed and moves the game into the
    ReviveOffer / Lost state.

NOTES
-----
  - baseTxt is NOT null-checked in Start or in ApplyDamageToPlayerGate, unlike
    healthBar. A gate prefab without the label assigned will throw a
    NullReferenceException on the first hit.
  - Because it is a STATIC event, a subscriber that fails to unsubscribe will
    leak across scene loads. LevelGameManager correctly unsubscribes in
    OnDisable.

CHANGED 2026-09-12 - a base in a WINNING battle is DAMPED, not immune
---------------------------------------------------------------------
ApplyDamageToPlayerGate no longer returns early, and no longer asks whether the
base still has living defenders. It asks CPBattleController.BattleIsAnExpectedWin,
and while that is true it takes LevelBattleRules.BaseChipPerBlow (1%) of its
MAXIMUM health per connected blow.

    battle the player is meant to WIN     ->  1% of max per blow
    battle the player is meant to LOSE    ->  NORMAL weapon damage
    no prepared battle (stage 6+, or a    ->  NORMAL weapon damage
      scene entered directly)

Why damped at all: an enemy that walked past the duel and hammered the castle
produced no health drop and no bar movement, which reads as a broken game rather
than as a rule - reported in levels 2 and 3, where one enemy peels off while the
hero is busy. One percent is visible feedback that decides nothing: felling a base
that way needs a hundred blows, far longer than these battles run.

Why gated on the OUTCOME (Arash, 2026-09-12): in a battle the player is meant to
lose, that loss is the point, and damping the base leaves the match unable to end
the way the workbook says it must. The previous condition - "while the base still
has living defenders" - answered the wrong question. It damped the LOSING battles
right up until the last hero fell, then let the base fall at full speed in exactly
the battles that were never in danger anyway.

It cannot strand a battle. The champion cannot die in a prepared win - its reserve
floor in CPBattleController.LimitDamageToChampion sees to that - so a "should win"
battle always still has a hero standing to finish it.

The ENEMY gate deliberately keeps full immunity while its own defenders live
(CPBattleController.HasLivingDefenders, now its only caller). Destroying it ends the
level in a WIN, so letting a stray hero chip it would be an outcome bug rather than
cosmetic - it could finish a match the workbook says must be a loss.
