PURPOSE
-------
Defines what it costs to upgrade a unit from level L to L+1 in BOTH resources -
COINS (GetCostForLevel) and HERO XP (GetHeroXpCostForLevel) - and where the level
cap sits. Pure economy tuning data.

NOT gems. Gems are never spent on unit upgrades; PlayerProgressionService.TryUpgrade
charges CurrencyManager.TrySpendUpgradeResources(coins, heroXp). The older docs and
the OnUnitUpgraded event argument named "spentGems" are both misleading on this.

Both wallets are SHARED across all heroes (SaveData.coins / SaveData.heroXp), so the
rising per-hero cost curve is the mechanism that makes spreading upgrades across the
deck cheaper than funnelling them all into one hero. See NOTES.

TYPES
-----
  enum Mode
    Geometric           cost(L) = ceil(baseCost * ratio^(L-1))
    PiecewiseGeometric  cost(L) = ceil(baseCost * product of per-segment ratios)
    Both are now only the FALLBACK - see authoredCoinCosts below.

  struct Piece   { fromLevelInclusive, toLevelInclusive, ratio }
      One segment of the piecewise curve.
      NOTE: this type is named "Piece", which COLLIDES conceptually with the
      puzzle-board Piece class. Both live in the global namespace. They compile
      because this one is nested inside UpgradeCostSO, but it is confusing when
      reading code - see the project's namespace recommendation.

FIELDS
------
  mode        (Mode, default Geometric)      fallback only
  levelCap    (int, default 50)              maximum level a unit can reach
  baseCost    (int, default 2; asset: 40)    fallback only
  ratio       (float 1.0-2.0; asset: 1.5)    fallback only, Geometric mode

  authoredHeroXpCosts  (List<int>)  Hero XP cost of the first N upgrades, in order.
              Live asset: 1, 2, 3, 4, 4, 5, 5, 6
              Non-empty => WINS over firstHeroXpCost/heroXpCostStep.
  firstHeroXpCost (int, 1)  } legacy linear fallback, reached only when
  heroXpCostStep  (int, 1)  } authoredHeroXpCosts is emptied.

  authoredCoinCosts    (List<int>)  Coin cost of the first N upgrades, in order.
              Live asset: 50, 80, 200, 340, 580, 1000, 1700, 2900
              Non-empty => WINS over mode/baseCost/ratio.
              The jump at entry 3 (80 -> 200, x2.5) is DELIBERATE: it is what stops
              a player buying a third upgrade on a single hero before stage 6.

  pieces      (List<Piece>) Ratio bands. Used by PiecewiseGeometric mode AND as the
              tail that continues authoredCoinCosts past its last entry. Live asset:
                  levels 1-15   ratio 1.50
                  levels 16-25  ratio 1.35
                  levels 26-50  ratio 1.20
              i.e. cost growth SLOWS at higher levels. This decay is REQUIRED: a flat
              ~1.7 ratio held to level 50 reaches ~1e13 coins and overflows int.

METHODS
-------
  IsAtCap(currentLevel) -> bool
      True when the unit can no longer be upgraded.

  GetHeroXpCostForLevel(currentLevel) -> int
      0 at cap. Authored table if in range; past its end returns floor(L/2) + 2,
      which extends the authored shape (…,6 -> 6, 7, 7, 8, 8, …). Falls back to the
      linear firstHeroXpCost + (L-1)*heroXpCostStep only if the table is empty.

  GetCostForLevel(currentLevel) -> int
      0 at cap. Authored table if in range; past its end it multiplies the LAST
      authored value by GetPiecewiseRatioForLevel(k) for each k past the table.
      Falls back to Geometric / PiecewiseGeometric only if the table is empty.

  GetPiecewiseRatioForLevel(level) -> float  [private]
      Finds the segment containing 'level'. If none matches it falls back to the
      LAST segment's ratio (or 1.0 if the list is empty), so a gap in the
      segment table silently uses the final ratio rather than erroring.

  OnValidate()  [Editor only]
      Clamps levelCap and baseCost to >=1, clamps every entry of BOTH authored
      tables to >=1 (a 0 entry would hand out a free upgrade), fixes segments where
      'to' < 'from', and clamps every ratio into 1.0-2.0.

HOW IT CONNECTS
---------------
  - Injected into PlayerProgressionService by GameStartManager; read by
    GetUpgradeCost / GetUpgradeHeroXpCost / CanUpgrade / TryUpgrade.
  - UnitsPanelController (field at ~L33) displays the cost and the current-vs-next
    stat preview from here.
  - CurrencyManager.TrySpendUpgradeResources(coins, heroXp) actually charges both.
  - StageRewardCalculator.EarlyHeroXp is the matching FAUCET. The two are tuned as a
    pair - changing one alone breaks the milestones below.
  - EarlyCampaignAuthoring.Apply() ("Tools/Balance/Author Stages 5-10") REWRITES all
    of these values. Edit the Inspector and that menu item will revert you unless the
    script is updated too.
  - EarlyCampaignEconomyVerification.Run() asserts the resulting economy.

NOTES
-----
  - Tuning intent (verified 2026-09-21, minimum-HP income):
      by stage 5: 200 coins /  5 XP  -> four heroes buy upgrade #1 (200 coins, 4 XP)
      by stage 9: 540 coins / 12 XP  -> four heroes buy upgrade #2 (320 coins, 8 XP)
      one hero alone is stopped at TWO upgrades: a third costs 200 coins on top of
      the 130 already spent, against 270 banked (324 at all-full-HP clears).
  - Mathematical limit, do not chase it: with a single shared wallet you can cap the
    tunnelling player one upgrade above the spread, but you can NEVER block a third
    upgrade on one hero while still letting all four heroes reach level 3.
  - Hero XP is currently granted on EVERY win (WinPanel.cs ~L369) with no first-clear
    gate, so a player who replays cleared stages farms it without limit. While that
    holds, these cost curves bound a bad build's cost in TIME, not absolutely.
  - The tail loop multiplies once per level past the table on every call. Cheap at
    cap 50 and called from UI refreshes, but it is not cached.
