*** STATUS: REVIVE IS DISABLED  (2026-09-06) ***
------------------------------------------------
  private static readonly bool OfferRevive = false;   (top of the class)

  EnterDefeatFlow() now ALWAYS takes its Lose branch: a dead player gate, or a
  mutual wipe, shows the Lose panel immediately. GameState.ReviveOffer is never
  entered, and NotifyReviveAccepted / NotifyReviveDeclined are never called
  (RevivePanel was their only caller and its own revive paths are switched off
  too). Consequently hasRevivedThisStage stays false forever, and
  suppressStalemateUntil / postReviveSettleSeconds are never armed.

  Nothing was deleted. To restore the old flow, set OfferRevive here AND
  ReviveEnabled in RevivePanel to true.

  Deliberately static readonly, not [SerializeField]: the scenes already carry a
  serialized allowSingleRevivePerStage = true, and a second Inspector toggle is
  the kind of thing that gets flipped back on by accident in one stage out of
  twenty.

PURPOSE
-------
The stage-level game-flow state machine: Playing / Won / ReviveOffer / Lost
(ReviveOffer now unreachable - see STATUS above). It is the single place that
listens for BOTH gates being destroyed and decides what happens next - show the
win panel or go straight to lose.

Since 2026-08-30 it also owns a THIRD end-of-level path that no gate can raise:
the mutual-wipe check (see MUTUAL WIPE below).

STATE ENUM
----------
  GameState { Playing, Won, ReviveOffer, Lost }
  CurrentState  (public get / private set, default Playing)

SINGLETON
---------
  Instance  guard-and-destroy in Awake. NOT DontDestroyOnLoad - a fresh instance
            is expected in every gameplay scene, which matches ResetForNewStage
            existing as an alternative to a full scene reload.

INSPECTOR FIELDS
----------------
  winPanel      (WinPanel)
  revivePanel   (RevivePanel)
  allowSingleRevivePerStage (bool, default true)

  Stalemate (mutual wipe)  [2026-08-30]
  detectMutualWipe        (bool, default true)  master switch for the third
                          end-of-level path. OFF restores the old behaviour
                          (and the old hang).
  stalemateGraceSeconds   (float, default 2.5)  the wipe must hold this long
                          uninterrupted before the level ends. This is the
                          window a gem buy-back has to land in.
  postReviveSettleSeconds (float, default 5)  the check is skipped for this
                          long after a revive is accepted.

RUNTIME STATE
-------------
  hasRevivedThisStage (bool)
  playerGate  (PlayerGateStats, found in Start)
  enemyGate   (EnemyGateStats, found in Start)
  enemySpawner (EnemySpawner, found in Start, includeInactive)
  stalemateTimer (float)  how long the wipe condition has held unbroken
  suppressStalemateUntil (float)  UNSCALED timestamp before which the wipe
                          check is skipped entirely

LIFECYCLE
---------
  Awake()   singleton guard
  OnEnable / OnDisable
      Subscribe/unsubscribe BOTH EnemyGateStats.OnGateDestroyed ->
      OnEnemyGateDestroyed AND PlayerGateStats.OnGateDestroyed ->
      OnPlayerGateDestroyed - correctly paired.
  Start()   finds both gates via FindObjectOfType (not null-checked afterward,
            but only read inside OnEnemyGateDestroyed's HP% calculation, which
            null-checks playerGate defensively), plus the EnemySpawner used by
            the mutual-wipe check
  Update()  the mutual-wipe watchdog - see MUTUAL WIPE below. Does nothing at
            all unless CurrentState is Playing.

ENEMY GATE DESTROYED -> WIN
-------------------------------
  OnEnemyGateDestroyed()
      Ignored if CurrentState is not Playing (guards against double-firing).
      Sets CurrentState = Won.
      EXPLICITLY DOES NOT call GameplayPause.SetPaused(true) - the extensive
      inline comments explain why: player units already individually freeze via
      PlayerManager.HandleGateDestroyed reacting to the SAME static event, and
      the reward UI animations (coins/gems/XP flying in) need Time.timeScale to
      keep running normally.
      Computes hpPercent = playerGate.currentHP / playerGate.maxHealth
      (clamped 0..1, defaulting to 1 if the gate reference is missing).
      Calls HomeManager.NotifyStageWon(hpPercent) - the progression/star-saving
      hookup.
      Activates and calls winPanel.Show(hpPercent).

PLAYER GATE DESTROYED -> LOSE
--------------------------------------------
  OnPlayerGateDestroyed()
      Ignored if not Playing. Otherwise delegates straight to EnterDefeatFlow().

  EnterDefeatFlow()   [2026-08-30 - extracted from the above]
      THE one defeat path, shared by the gate death and the mutual wipe. Callers
      own the "are we still Playing?" guard.
      UNLIKE the win path, this DOES call GameplayPause.SetPaused(true) -
      losing is meant to fully freeze the game.
      Condition: if (!OfferRevive || (allowSingleRevivePerStage &&
      hasRevivedThisStage)) -> Lost + revivePanel.ShowLosePanel().
      [2026-09-06] Since OfferRevive is false, the leading !OfferRevive makes
      this branch UNCONDITIONAL - every defeat lands on the Lose panel at once.
      The else-branch (ReviveOffer + revivePanel.ShowRevivePanel()) is kept
      intact but unreachable.

MUTUAL WIPE -> SAME DEFEAT FLOW, NO GATE INVOLVED   [2026-08-30]
---------------------------------------------------------------
  THE BUG THIS FIXES: normally one surviving side always resolves the battle -
  leftover enemies march on the player gate, leftover heroes march on the enemy
  gate. But if the LAST hero and the LAST enemy kill each other, and the spawner
  has no waves left, both gates are still standing and NOTHING can ever raise
  OnGateDestroyed again. The stage hung in Playing forever, with no panel. That
  state is now a DEFEAT, routed through the exact same EnterDefeatFlow the
  player gate uses - i.e. straight to Lose since 2026-09-06.

  Update()
      Zeroes stalemateTimer and returns unless detectMutualWipe is on,
      CurrentState is Playing, Time.unscaledTime has passed
      suppressStalemateUntil, and IsMutualWipe() is true. Otherwise it
      accumulates unscaled delta time and calls EnterDefeatFlow() (after one
      Debug.Log) once stalemateGraceSeconds has elapsed.
      The grace timer is what makes the gem buy-backs safe: a LastStandOffer /
      HeroStatsPanel purchase landing inside the window pushes
      HeroRoster.TotalAlive() above 0 and resets the timer. Past the window the
      level ends regardless of gems held - that is the intended design.

  IsMutualWipe()   ALL of these must hold:
      - enemySpawner exists, BattleStarted AND HasSpawnedFirstEnemy. This single
        check is what keeps everything inert through the puzzle-only phase.
      - enemySpawner.AllWavesDispatched - otherwise the field being empty just
        means we are BETWEEN waves.
      - playerGate alive (!isPlayerGateDestroyed) and enemyGate alive
        (!isDestroyed) - a fallen gate is the gate events' business, not ours.
      - HeroRoster.TotalAlive() == 0. That counts only heroes actually RELEASED
        into the field (isUnlocked), and PlayerWaveManager marks a bought
        reinforcement unlocked before its gate hold, so a hero on its way in
        correctly keeps this above zero.
      - enemySpawner.AliveEnemyCount == 0 AND AnyLiveEnemyInScene() is false.
        The cheap counter runs first; the FindObjectsOfType<EnemyStats> sweep
        only executes on the rare frames where both sides already read empty,
        and exists to catch enemies hand-placed in a scene that the spawner
        never counted. EnemyGateStats derives from CharacterStats, not
        EnemyStats, so the gate itself is never mistaken for a live enemy.

REVIVE CALLBACKS  (called BY RevivePanel, not internally)
--------------------------------------------------------------
  [2026-09-06] BOTH ARE NOW DEAD. RevivePanel was their only caller and its
  revive paths are switched off, so neither ever fires. Kept, not deleted.

  NotifyReviveAccepted()
      Sets hasRevivedThisStage = true and CurrentState back to Playing. Per the
      comment, RevivePanel itself is responsible for calling
      GameplayPause.SetPaused(false) after actually reviving - this method only
      updates the state flag.
      ALSO arms suppressStalemateUntil = unscaledTime + postReviveSettleSeconds
      and zeroes the timer. REQUIRED: RevivePanel.ReviveTheStage() destroys
      every locked hero and restarts PlayerWaveManager, so the field really is
      empty for a second or two - without this the mutual-wipe check would
      re-declare defeat the instant the player paid to come back.

  NotifyReviveDeclined()
      Sets CurrentState = Lost. Gameplay remains paused; the Lose panel (already
      shown by RevivePanel at this point) stays up.

  ResetForNewStage()
      Resets CurrentState to Playing, clears hasRevivedThisStage and both
      stalemate timers - an
      alternative to destroying/recreating this object if a stage is replayed
      without a full scene reload.

HOW IT CONNECTS
---------------
  - EnemyGateStats.OnGateDestroyed / PlayerGateStats.OnGateDestroyed are the two
    inputs - both static events raised deep in the Combat layer, consumed here
    without any direct reference needed.
  - HomeManager.NotifyStageWon is called on win - the actual star/progress save
    happens over there.
  - WinPanel.Show / RevivePanel.ShowRevivePanel / RevivePanel.ShowLosePanel are
    the three UI entry points this class drives.
  - RevivePanel calls back into NotifyReviveAccepted/NotifyReviveDeclined.
  - EnemySpawner is POLLED read-only every frame (BattleStarted,
    HasSpawnedFirstEnemy, AllWavesDispatched, AliveEnemyCount) for the
    mutual-wipe check; HeroRoster.TotalAlive() supplies the hero half.

NOTES
-----
  - A dead numbered sibling GameState existed only as a NAME COLLISION risk, not
    a duplicate class: Core/SaveLoad/GameState.cs ALSO declares a (unrelated)
    static class named GameState in the global namespace, while this file
    declares a nested enum GameState inside LevelGameManager. They do not
    actually collide at compile time because one is nested, but the shared name
    is confusing when searching the codebase.
  - Because this is a per-scene singleton (no DontDestroyOnLoad), reloading the
    gameplay scene naturally gives a fresh instance with CurrentState reset to
    Playing - ResetForNewStage exists for the case where the SAME scene
    instance is reused instead.
