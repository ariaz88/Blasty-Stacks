PURPOSE
-------
Turns a ProgressionConfigSO curve set plus a unit level into concrete multipliers
for each stat. Pure math - no Unity objects, no side effects.

TYPES
-----
  struct Growth { gA, gH, gAS, gD }
      Multiplier for Attack, HP, AttackSpeed, Defense.
      A value of 1.0 means "no change".

      There is NO gMv. moveSpeed does not grow at all - Arash's directive
      2026-09-10. Movement is a flat 0.3 for every unit on both sides and is not
      part of progression. This also removed a real problem: enemy level = stage
      number, so a growing moveSpeed made enemies outpace heroes late in the
      campaign, since a hero only levels on upgrade.

      There is NO gR either. Attack range has no growth axis: it is excluded from
      CP and from progression, and the stat-block value is never read in combat
      (players use PlayerManager.maxAttackRange, enemies their stopping distance).
      See A2 in Docs/cp-analysis/NEXT_VERSION_CHANGES.md.

METHODS
-------
  GetGrowthMultipliers(int level, ProgressionConfigSO cfg) -> Growth
      Walks every level from 2 up to 'level' and COMPOUNDS the per-level percent:
          multiplier = product over l=2..L of (1 + pct(l))
      Returns all-1.0 if cfg is null or level <= 1, so level 1 is always base.
      Each evaluated percent is clamped by cfg.pctClamp before being applied.

  ClampPct(v, clampRange)  [private]
      Mathf.Clamp helper.

HOW IT CONNECTS
---------------
  - PlayerProgressionService uses it to preview "current vs next level" stats
    in the unit upgrade UI.
  - PlayerStatsApplier applies all five multipliers when building a hero's
    runtime stats.
  - EnemyManager.RebuildFromBase applies only four of the five - g.gD (defense)
    is still missing there. See D2 in Docs/cp-analysis/NEXT_VERSION_CHANGES.md.

NOTES
-----
  - The loop is O(level). It is called from UI code, so at very high levels this
    is a linear cost per query. Fine at the current cap, worth caching if levels
    ever reach the hundreds.
  - UnitStatsRuntime.ApplyLevelGrowth computes the same idea independently with
    Mathf.Pow instead of this compounding loop, and has ZERO call sites. Do not
    assume it runs at spawn - it does not.
