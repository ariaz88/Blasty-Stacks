PURPOSE
-------
Plays the "you earned these heroes" CARD animation that REPLACED heroes spawning
onto the gate platforms.

Before PHASE 2 every puzzle match instantiated heroes on the four gate platforms
and made them leap into the battlefield. Three or four matches filled the field,
which made the scene unreadable and the stage far too easy - and no amount of CP
tuning fixed it, because it is a RATE problem, not a stat problem.

The heroes are still earned at exactly the same rate
(LevelBattleRules.Deployments - stage 4 is still 1,1,2,4). They are now held in
data by PlayerWaveManager and ANNOUNCED by this card deal instead of being
instantiated.

This script is PRESENTATION ONLY. It owns no roster state and never decides how
many heroes anything gets - it renders whatever PlayerWaveManager.HeroesEarned
hands it. Getting those heroes into the battle is a separate, still-undesigned
step.

THE BEATS AS BUILT (seconds)
----------------------------
  0.00-0.18  cards RISE IN FROM BELOW and gather, FACE DOWN, at the left [fr.1-3]
  0.18-0.34  each card flips to its real hero portrait (0.035s stagger)
  0.34-0.62  they fan out along a shallow arc to centre, face up         [fr.3-9]
  0.62-0.86  the fan HOLDS - the beat the player actually reads
  0.86-1.00  cards collapse back into one stack at centre                [fr.9-11]
  1.00-1.06  white flash                                                 [fr.12]
  1.06-1.20  resolves to ONE teal-glowing card, back to "?"              [fr.13]
  1.20-1.55  the glow holds                                              [fr.15-22]
  1.55-1.80  fade out

The flip and the read-hold are ADDITIONS, not in Ref1: unlike the reference,
these cards have to tell the player WHICH heroes were earned. Order confirmed
with the user 2026-09-14 ("first all backs, then real portraits, and when it
turns blue the '?' again") and flagged as possibly changing later.

CONSTANTS (all authored at the top of the file)
------------------------------------------------
  Tempo       1.0833 ONE dial for the whole pace; ABOVE 1 is SLOWER. Every beat is
                     a multiple of it, so scaling it keeps the beats in proportion
                     and keeps the absolute timestamp (THoldEnd) consistent with
                     the durations. 1.0 = the Ref1 timing (1.80s single-card run).
                     !! THE TOTAL IS REPORTED, NOT PINNED - see NOTES.
                     A multi-card deal runs slightly longer: the flip is staggered
                     per card, so add TFlipStagger * (cards - 1).
                     MEASURED: 1 card 1.869s / 2 cards 1.907s / 4 cards 1.982s.
  Timeline    base values, each multiplied by Tempo:
              TFlyIn .18 / TFlipDur .16 / TFlipStagger .035 / TFanStart .34 /
              TFanDur .28 / THoldEnd .86 / TCollapseDur .14 / TFlashDur .06 /
              TGlowIn .14 / TGlowHold .35 / TFadeOut .25
  CardWidthFraction      0.20   card width as a fraction of screen width
                                (measured off Ref1)
  CardAspect             256/358  matches the baked sprites; playing-card 2.5:3.5
  ClearanceInCardHeights 1.55   how far ABOVE the player base the deal sits. THE
                                ONLY knob that moves the presentation vertically -
                                the gather point, the fan and the entry point are
                                all relative to this anchor, so changing it
                                translates the whole deal as one piece and leaves
                                every internal distance intact.
  FanStepInCardWidths    0.62   <1 so fanned cards overlap like a held hand
  FanTiltDegrees         13     tilt of the OUTERMOST cards
  FanArcInCardHeights    0.10   how high the fan's middle arcs above its ends
  EntryRiseInCardHeights 2.4    how far BELOW the gather point the cards start
  PortraitFillFraction   0.80   portrait size as a fraction of the card
  TealGlow  #38E1F0    TealCard #7CECF7

REVISION 2026-09-14 (after the first play-test recording,
"Assets/Arts/Reference videos/Card Animation REcord.mkv")
  1. CARDS NOW RISE FROM BELOW. The first build dropped them in from above the
     screen; Ref1 deals from the LOWER part of the frame and the drop read as the
     opposite gesture. They now start EntryRiseInCardHeights below the gather
     point - roughly behind the player base, so the heroes come UP out of your own
     base rather than flying the whole height of the screen across the board.
  2. THE CARD SHOWS ONLY THE PORTRAIT. It used to clone the authored "Cell Active"
     frame onto the face. On screen that read as a card INSIDE a card: the blue
     panel competed with the card frame and buried the hero. The clone, and with
     it the whole HeroStatCell dependency, is gone - the face now carries a single
     Image holding UnitDefinitionSO.portrait, preserveAspect on.
  3. RE-TIMED: Tempo 1.0833 (1.80s off Ref1 -> 2.07s -> 1.95s), then the FADE-OUT
     alone cut 30% (base 0.25 -> 0.175, i.e. 0.271s -> 0.190s) because the teal
     card's fade dragged against everything before it. Single-card run is now
     1.869s.
  4. THE WHOLE DEAL MOVED DOWN 0.45 card heights (ClearanceInCardHeights 2.00 ->
     1.55): at 2.00 the cards sat against the top edge of the screen. Measured:
     anchor y 733.5 -> 610.4, a drop of 123.1 canvas units = 0.45 * cardH, which
     is 5.8% of screen height. Entry and fan distances are unchanged - the anchor
     carries them.

FLOW
----
  Bootstrap()  [RuntimeInitializeOnLoadMethod, AfterSceneLoad]
      Creates "[HeroCardRevealDirector]". Nothing to wire in a scene - same
      pattern as ShardBurst. DontDestroyOnLoad only when Application.isPlaying;
      in edit mode it sets HideFlags.DontSave instead, because DontDestroyOnLoad
      THROWS outright from an editor script.

  OnEnable / OnDisable
      Subscribe / unsubscribe PlayerWaveManager.HeroesEarned. The event is static
      and PlayerWaveManager never clears it, so the unsubscribe is MANDATORY.

  HandleHeroesEarned(heroes, anchorWorld)
      ENQUEUES the reward and starts DrainDealQueue if it is not already running.

  DrainDealQueue()  [coroutine]
      Plays every queued deal back to back. Holds IsDealing for the WHOLE queue,
      not per deal, so the board cannot be touched in the gap between two rewards.

  !! DEALS QUEUE - THEY MUST NOT CANCEL EACH OTHER. The first version called
  StopCoroutine on the running deal and restarted, with a comment claiming awards
  "arrive one at a time, so this is a safety net, not the normal path". THAT WAS
  WRONG and measurably so: PlayerWaveManager's planned loop waits only
  `nextWaveDelay` (0.75s default, PlayerWaveManager.cs:23) between awards, while a
  full deal is ~1.87s. One piece placement that clears TWO matches bumps
  MatchesCleared by two, both `while (MatchesCleared < match)` guards fall through
  at once, and the second award lands ~0.75s into the first deal. The board-input
  gate does NOT prevent it, because both matches came from a placement that had
  already resolved. Cancelling threw away the first match's cards mid-animation,
  so the player never saw what that match earned.

  PlayDeal no longer touches IsDealing or `playing` - DrainDealQueue owns both.
  OnDisable clears the queue, or a deal queued before a scene change would replay
  the previous stage's reward over the new one.

  PlayDeal(heroes, anchorWorld)  [coroutine]
      Runs the beats above. Uses Time.unscaledDeltaTime and
      WaitForSecondsRealtime throughout, so the deal still plays if the game is
      paused (Time.timeScale = 0) during the presentation.

  MeasureLayout(anchorWorld, out cardW, out cardH, out anchor)
      Forces a canvas layout pass, THEN measures. See NOTES !! - this is not
      optional.

  ComputeFan(n, anchor, cardW, cardH, out pos, out rot)
      u runs -1 (leftmost) .. +1 (rightmost); a single card sits dead centre with
      no tilt. The (1 - u*u) term lifts the MIDDLE of the fan, which is what makes
      it read as a held hand rather than a straight row. Shared by the runtime
      deal and the editor preview so the two can never drift.

  ResolveAnchor(anchorWorld, cardH)
      WorldToScreenPoint -> canvas local, then + ClearanceInCardHeights * cardH,
      then clamped to keep the fan on screen on a short phone.

  EnsureCanvas()
      Builds a ScreenSpaceOverlay Canvas at sortingOrder 900 with a
      ScaleWithScreenSize scaler (1080x1920, match 0.5), a CanvasGroup with
      blocksRaycasts = false, a "Stage" child and the white "Flash" image.

  CardView.Build(parent)  [nested class]
      Card = Glow (behind) + Face + cloned "Cell Active" avatar frame + Back.

BOARD INPUT GATE
----------------
  IsDealing  [public static]  true from the first card rising to the last frame
  of the fade. BoardInputController.Update early-returns on it, so no piece can be
  picked up while the cards are on screen. Without it the player can start a
  SECOND match underneath the cards the moment the first one resolves, which hides
  the reward and overlaps two deals.

  !! IT IS CLEARED IN OnDisable AS WELL AS AT THE END OF THE DEAL. The flag is
  static and gates input: a deal interrupted by a scene change, a level ending or
  the object being destroyed mid-animation would otherwise leave it true forever
  and the board could never be touched again.

  TickSettle() still runs while the gate is closed - freezing it would strand a
  stack mid-slide.

EDITOR-ONLY API  (#if UNITY_EDITOR)
-----------------------------------
  EditorPreviewFan(count, faceUp, anchorWorld) -> string
      Builds the canvas and poses N cards at the fan's REST pose so the layout can
      be screenshotted and tuned WITHOUT Play mode. Returns the measured canvas
      size, card size, anchor, fan width and fan top for checking against the
      authored targets. Exists because the coroutine needs a real deltaTime, which
      edit mode does not provide - stepping it manually would hang.
  EditorTimelineReport(cards) -> string
      The real beat durations and the total run, summed from the SAME constants
      PlayDeal uses. Check a re-timing against the intended total with this rather
      than trusting the arithmetic by eye.
  EditorPreviewCanvas   the live preview canvas, for screenshot tooling
  EditorPreviewCleanup() destroys EVERY edit-mode preview object - see NOTES !!
  EditorInstallPreviewGuard()  [InitializeOnLoadMethod] registers that cleanup on
      assembly reload and on play-mode transitions, and sweeps immediately.

HOW IT CONNECTS
---------------
  - Subscribes to PlayerWaveManager.HeroesEarned (static) - the ONLY inbound
    coupling. It does not reference the wave manager otherwise.
  - Reads UnitDefinitionSO.portrait, the same sprite HeroStatCell.Bind writes.
    That is now the ONLY thing it takes from the units data - as of the 2026-09-14
    revision it does not touch HeroStatCell or HeroStatsPanel at all.
  - Sprites come from Assets/Arts/VFX/HeroCard{Back,Face,Glow}.png, baked by
    CardBackSpriteBaker.

NOTES / RISKS
-------------
  - !! CANVAS RECT IS STALE ON THE FRAME IT IS CREATED. Measuring
    canvasRect.rect straight after building the canvas returned 1125 wide on the
    first deal and 979 on every one after, which sized the cards differently each
    time and put the second deal COMPLETELY OFF SCREEN (verified: an empty
    capture). EnsureCanvas and MeasureLayout both call Canvas.ForceUpdateCanvases
    before any measurement. Do not remove either call.
  - !! Object.Destroy DOES NOT WORK IN EDIT MODE - it is deferred to end of frame,
    which edit mode never reaches, so it logs an error and the object survives.
    SafeDestroy picks DestroyImmediate when not playing. The editor preview hits
    this path while stripping Buttons off the cloned template.
  - !! This is uGUI, NOT a ParticleSystem, so none of the URP-2D particle
    constraints in the VFX Playbook apply here. A ScreenSpaceOverlay canvas is
    also INVISIBLE to Unity_Camera_Capture - to screenshot it, temporarily switch
    renderMode to ScreenSpaceCamera and render a camera into a RenderTexture whose
    ASPECT MATCHES THE CANVAS, or the capture silently crops.
  - !! THE EDITOR PREVIEW CAN ORPHAN ITSELF, AND THE ORPHAN IS VISIBLE IN EVERY
    SCENE. EditorPreviewCleanup originally destroyed the object through the static
    `instance`. A domain reload - which EVERY script compile causes - resets that
    static to null while the GameObject lives on, so nothing could clean it up.
    HideFlags.DontSave keeps such an orphan out of the scene file (it never shows
    in a diff or a build) but it KEEPS RENDERING in the Game view over every
    scene, which looks exactly like a gameplay bug. Happened 2026-09-14: two blank
    face-up cards sat over the HUD in every scene with isPlaying == false.
    Cleanup now sweeps by TYPE (Resources.FindObjectsOfTypeAll) and is registered
    on beforeAssemblyReload and playModeStateChanged. Never route it through a
    static handle again.
  - !! DO NOT DERIVE Tempo FROM A TARGET TOTAL. It briefly was
    (Tempo = TargetRunSeconds / BaseRunSeconds), which meant shortening any ONE
    beat silently STRETCHED every other beat to refill the target - the exact
    opposite of what tuning a single beat is for. Tempo is now an explicit pace
    dial, individual beats are tuned on their own, and the resulting total is read
    back with EditorTimelineReport.
  - !! AN IMAGE WITH A NULL SPRITE DRAWS A SOLID WHITE QUAD. The portrait Image is
    built DISABLED and only enabled once a real sprite is assigned, so a hero with
    no portrait shows an empty card rather than a white block.
  - A null UnitDefinitionSO (or one with no portrait) deals a card with a blank
    face rather than throwing. This is what the editor preview shows in a scene
    with no GameStartManager.
  - Budget: at most TotalHeroes cards alive (4 on stage 4), pooled and reused
    across deals. No particles, no overdraw beyond a handful of quads.
