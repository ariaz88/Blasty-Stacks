CURRENT UPDATE - 2026-09-17  TARGETING: UNHANDLED BEATS NEAREST, AND TARGETS STICK
Two rules were added to UpdateTargetSelection (rewritten in full, see its section):
  1. A hero NEVER abandons a living target. `retargetHysteresis` is DELETED with
     the re-pick it guarded.
  2. When picking, an enemy NO other hero is handling outranks a closer one.
     Ranking lives in the new TargetClaimRegistry (fewest claimants, then nearest,
     then instance id) and is shared with TargetDetectionForPlayer.AcquireBestEnemy.
OnEnable/OnDisable now Register/Unregister this hero with TargetClaimRegistry.
A hero's claim IS its currentTarget field - there is no separate claim object and
nothing to release. Read TargetClaimRegistry.txt before changing either rule.

PREVIOUS UPDATE - 2026-09-16  A HERO MOVES AT ONE CONSTANT SPEED
`marchSpeedBoost` (1.3) and the `MarchSpeed` property are DELETED. Both movement
paths now use CurrentMoveSpeed:
    HandleRoamForward   (no target)  -> dir * CurrentMoveSpeed
    HandleMoveToTarget  (has target) -> dir * CurrentMoveSpeed
The only thing that may change a hero's speed is a full STOP - combat, attacking,
the deploy lock (Arash's directive).

THE BUG IT FIXES. HandleRoamForward used MarchSpeed while HandleMoveToTarget used
CurrentMoveSpeed, so a hero travelled at 0.78 with no target and dropped to 0.60 the
instant it locked one. Killing an enemy produced a visible 23% slowdown as the hero
turned to chase the next. Reported by Arash from play, then confirmed in the code.

WHY IT MUST NOT COME BACK. The boost was added because the long march READ as slower
than the short approach - even though both measured a steady 0.6, the real cause
being distance and the absence of course changes. Fixing a perception problem with a
real speed change produced three faults:
  * a unit that changes speed on invisible state reads as broken;
  * moveSpeed is excluded from CP on the grounds that it does not decide a fight -
    only true while it is CONSTANT. A hero closing 30% faster while untargeted
    reaches the next enemy sooner and takes less fire on the way, which CP cannot see;
  * enemies have no equivalent, so the hero was 20% faster than an enemy while
    chasing but 56% faster while roaming.
If the march feels sluggish again: shorten the lane, or raise the authored moveSpeed
on BOTH sides. A visible number, never a hidden state multiplier.

OTHER THINGS THAT STILL AFFECT EFFECTIVE SPEED (none of them change the speed value):
  1. CrowdSeparation2D.SteerAroundBlockers (avoidStrength 0.9) bends the travel
     DIRECTION up to ~42 degrees around an ally, so forward progress toward the
     target drops to about 74% while a blocker is close. Allies only, never enemies.
  2. ResolveAttackDestination sends each attacker to its own slot on an arc AROUND
     the target, so the path is longer than a straight line.
  3. MeleeContactRecovery.IsRepositioning makes FixedUpdate return BEFORE the state
     machine; the body is then driven by MovePosition and the damage collider is
     disabled. Fires after 2.5s without contact, lasts up to 1.1s.
Authored speeds for reference: every hero 0.60, every enemy 0.50 - NOT equal,
despite an older note in SESSIONS.md claiming they are.

PURPOSE
-------
Stage 1-5 addition: FixedUpdate temporarily defers state-machine movement/attacks
while MeleeContactRecovery is making a physical sidestep after missed contact.

The player unit's central hub. Unlike EnemyManager (which does all its own
decision logic), PlayerManager mostly HOSTS the state machine and provides
shared services to it: stats, target detection, facing, movement toward a
target with friendly-separation steering, and damage application. The actual
decisions live in the PlayerState classes; this class is their toolbox.

[DefaultExecutionOrder(-100)] runs it early, before most dependent scripts.

      unitStats.moveSpeed when the stat block is built and > 0, else the
      serialized moveSpeed. Introduced by B1: before it, the Inspector value was
      the silent authority and unitStats.moveSpeed was never read at all, which
      is why the stat sheet said 3.5 while heroes actually walked at 0.5.
      The SO values are now 0.3 for players AND enemies (Arash's chosen base),
      and moveSpeed does NOT grow - ProgressionMath has no gMv, so 0.3 is the
      speed at every level for every unit until Arash says otherwise.

  AttackCadence(float recoveryTime) -> float
      Seconds to wait between swings = recoveryTime / attackSpeed, with
      attackSpeed floored at 0.05 so a zero stat cannot produce an infinite or
      negative cooldown. Introduced by B2: before it, cadence was the raw
      recoveryTime (a flat 0.6 on all ten PlayerAttackAction assets) and
      attackSpeed only set animator playback speed - so the stat contributed
      NOTHING to damage output. EnemyManager.AttackCadence mirrors this exactly;
      both factions must use the same rule or they are on different clocks.
      Every UnitStatsSO currently authors attackSpeed = 0.7 (Arash, 2026-09-10),
      so cadence is a uniform 0.6 / 0.7 = 0.857 s. Because the value is the same
      on both sides it shifts no balance; it simply makes every fight run ~43%
      longer than the old flat 0.6 s, and drops every CP by 30% uniformly.

LIFECYCLE
---------
  OnEnable / OnDisable
      Subscribe/unsubscribe EnemyGateStats.OnGateDestroyed -> HandleGateDestroyed.

  Awake()
      Caches every component reference, then calls EnsureDepthSorter(). Note
      enemyStats is resolved with FindAnyObjectByType<EnemyStats>() - it is
      assigned but never actually used anywhere else in the class; dead lookup.

  EnsureDepthSorter()   [private, from Awake]   (added 2026-09-11)
      Adds a UnitDepthSorter if the object has none, giving the hero a Y-driven
      draw depth so a unit standing in front is actually PAINTED in front. Every
      character part in the game sits on sorting layer Default at order 1, so
      without it the tie between two overlapping units resolves arbitrarily and an
      enemy's head can end up on top of the hero it is fighting.
      Skipped when CompareTag("PlayerGate") - the castle carries a PlayerManager
      but is not a unit. Done in code, not on the prefabs, because heroes are
      spawned from several places and none may ship without it.

  Start()
      Sets the Rigidbody2D to Dynamic, disables the damage collider, applies
      initial facing, and - IMPORTANTLY - sets unitStats = playerStatsApplier
      .CurrentStats. Unlike EnemyManager, PlayerManager does not build its own
      stats from statsBase; it simply borrows the reference already computed by
      PlayerStatsApplier (which itself handles roguelite multipliers).
      ALSO calls RegisterInHeroRoster() as its last act - see below.

  RegisterInHeroRoster()   [private, from Start]   (added 2026-08-22)
      Files this hero into HeroRoster under playerStatsApplier.unitId, and caches
      that id in rosterUnitId so OnDestroy can unregister from the SAME bucket
      even if the applier's unitId is rewritten later.
      Skipped entirely when CompareTag("PlayerGate") - the player castle also
      carries a PlayerManager and is not a hero - or when there is no applier.
      MUST stay in Start, not Awake: PlayerWaveManager calls SetUnitId() right
      after Instantiate, i.e. after Awake has already run, so registering earlier
      would file every hero under the prefab's default unitId.

  OnDestroy()   (added 2026-08-22)
      HeroRoster.Unregister(rosterUnitId, this) when rosterUnitId >= 0. Death
      reaches this 0.5s after PlayerDeathState schedules Destroy(gameObject,
      0.5f), so the "alive/total" label in the battle HUD drops as the body
      falls rather than the instant HP hits zero.

  HandleGateDestroyed()
      Clears attackPlayerGate/currentGateTarget, makes the Rigidbody2D kinematic
      and stops all motion, calls SetAnimMoving(false), calls
      HudCurrencyView.Instance?.PauseGameplay() (null-conditional, safe if the
      HUD singleton has not initialised), and transitions to
      playerGameCompleteState via ChangeStateSafe. The comment explicitly notes
      "NO global pause here" - only this unit freezes, unlike GameplayPause which
      stops the whole game.

  ChangeStateSafe(next)
      Guards against a null target or a redundant same-state assignment before
      calling SwitchToNextState.

FACING  (#region Facing Player)
--------------------------------
  SetVisualScale(factor)   scales visualRoot uniformly - used for pop/squash FX

  UpdateFacing()
      Freezes facing entirely while attacking or interacting (so a mid-swing
      character does not spin). Otherwise: if there is a real target and the
      unit is not locked, calls UpdateFacingAndOffset(); else falls back to
      SetFacingByScreenHalf().

  UpdateFacingAndOffset()  (the live version)
      Computes horizontal delta to the target, ignores movement smaller than a
      0.03 dead-zone, flips facing via FaceLeft(), and re-picks
      chosenEnemyOffset via currentTarget.GetOffsetFacingPlayer - keeping BOTH
      the sprite orientation and the approach slot synced to the same target
      side every frame.

  SetFacingByScreenHalf()
      Faces toward the SCREEN CENTER based on which half the unit currently
      occupies - so units entering from either side visually converge inward.

  FaceLeft(faceLeft)
      Flips transform.localScale.x, and (if there is a current target)
      re-resolves chosenEnemyOffset immediately - every facing change keeps the
      approach slot in sync.

Update()
--------
  1. Respects GameplayPause.
  2. HandleRecoveryTimer().
  3. Reads the animator's "isInteracting" bool (null-checked).
  4. If PlayerStats.playerIsdead, forces SwitchToNextState(PlayerDeathState)
     DIRECTLY - bypassing the normal Tick()-returns-next-state flow, since a
     dead unit must not wait for its current state to notice.
  5. UpdateTargetSelection() (see below).
  6. UpdateFacing() - the only facing call each frame.
  7. Recomputes distanceFromTarget from GetActiveTargetPosition() purely for
     Inspector debugging visibility.

UpdateTargetSelection() -> bool
--------------------------------
  THREE RULES then a two-phase search. Rewritten 2026-09-17.

  RULE 0 - A LOCKED HERO DOES NOT CHOOSE
      While isUnlocked is false the method clears currentTarget, resets
      hasEverDetectedEnemy and returns. A hero standing on its deploy gate picks
      nothing.

      THIS IS WHAT BROKE RULE 2 ON ITS FIRST PLAYTEST. Update() calls this every
      frame from the moment a hero is instantiated - roughly 1.2s BEFORE
      PlayerWaveManager.UnlockCurrentWave releases it - and
      TargetClaimRegistry.IsHandling deliberately ignores locked heroes, so a
      hero on a gate cannot reserve an enemy. Both halves are individually right
      and together they were a hole: a whole wave waiting on the gates saw
      "nobody is on anything", every hero picked the same nearest enemy, and rule
      1 then froze that choice for the rest of the battle. Arash's screenshot:
      two heroes on one enemy while the other walked at the base unopposed.

      Choosing at RELEASE makes the claims real. Heroes released in the same
      frame still run Update one after another, and OtherClaimants is counted
      live, so the second hero sees the first one's fresh claim.

  RULE 1b - THE ONE EXCEPTION: RE-BALANCE OFF A SHARED TARGET
      TryRebalance(), called only while the hero HAS a live target, at most every
      RebalanceInterval (0.5s). It moves the hero only when ALL FOUR hold:
        * the hero has NOT engaged yet (IsEngagedWithTarget false) - re-balance is
          an APPROACH-time decision only, see the engagement lock below;
        * its current target is SHARED (myOthers > 0) - a hero fighting alone
          never moves, so no fight is dropped on a whim;
        * the hero is NOT the closest one to that shared target
          (TargetClaimRegistry.IsNearestClaimant) - see the nearest-claimant lock
          below; and
        * some enemy has STRICTLY fewer other claimants.

      THE NEAREST-CLAIMANT LOCK (Arash, 2026-09-22). Reported right after the
      engagement lock went in, and it is the same bug one step earlier: the hero
      that turned around had not reached melee yet, so nothing held it. A hero
      walking at an enemy it was about to reach abandoned it for a brand-new
      spawn across the field, handing the enemy to an ally standing further back.

      Spreading out is the POINT of this method and Arash asked for it - but it
      is only spread if the enemy left behind ends up covered at least as well.
      Handing it to a hero further away is a straight downgrade: the enemy gets
      free time while the new owner walks in, and the hero that left spends that
      time walking too. Nobody gains.

      Exactly one hero per target passes IsNearestClaimant, so a doubled-up group
      still splits - the nearest keeps the fight, everybody behind it is free to
      cover the new wave. That is the distribution that was wanted all along.

      THE ENGAGEMENT LOCK (Arash, 2026-09-22). Reported from play: a hero already
      in melee walked away from the enemy it was hitting the moment a NEW enemy
      spawned. That was this method, and it was not a corner case - a fresh enemy
      enters the field with ZERO claimants, so every hero on a shared target sees
      a strict improvement in the same 0.5s tick and can leave a live fight with
      the enemy still standing behind it.

      The fix is a single early return on IsEngagedWithTarget. It removes ONLY the
      half of rule 1b that abandons a joined fight; heroes that are still WALKING
      re-balance exactly as freely as before - and walking is the case rule 1b was
      actually written for (the deployment-1 heroes that doubled up while wave 2
      marched in unopposed were marching, not fighting). It cannot deadlock: the
      lock holds only while the target lives, the target dies, and rule 1 then
      falls through to the persistent search, where the new enemy that triggered
      all this is ranked normally.

      WHY IT WAS NEEDED. Rule 2 fires only at the moment of picking, and that
      moment is often too early. Measured on level 4 from the [TARGET] log
      (2026-09-17): enemies arrive in TWO waves, so the first deployment
      correctly doubled up on the only enemy that existed - there was nothing
      else to choose - and rule 1 then held them there while wave 2 walked in
      unopposed. The rule was working; "decide once, at spawn" was not enough.

      WHY IT CANNOT OSCILLATE. OtherClaimants excludes self and is counted LIVE,
      so the instant a hero leaves, its old target reads one claimant fewer for
      everyone. Every switch strictly lowers the crowding of the hero that moves,
      and the hero left behind is then alone and will not move. Worked example,
      3 heroes on E1 and 1 on E2: the first to evaluate sees myOthers=2, finds E2
      at 1, moves; the next sees myOthers=1 against E2 at 2, no strict
      improvement, stays. Settles at 2/2 and stops. Using ">=" instead of ">"
      would re-create the five-times-registered swap bug.

  RULE 1 - A LIVE TARGET IS NEVER ABANDONED (except by rule 1b)
      If currentTarget exists and is not dead, the method returns immediately.
      Everything below runs only when the hero has nothing, or when what it had
      has died. This replaced a distance-hysteresis re-pick (retargetHysteresis,
      0.2 = "must be 20% closer"), which is DELETED.

      Stickiness is not a nicety - it is what makes rule 2 possible. Every other
      hero reads currentTarget as a CLAIM, and a claim that can be dropped for a
      marginal distance gain is not information anyone can act on. Worse, with
      claim-aware ranking a distance re-pick becomes an oscillator: two heroes
      comparing the same pair of enemies trade targets with each other forever.

  RULE 2 - AN UNHANDLED ENEMY BEATS A CLOSER ONE
      Candidates are ranked by TargetClaimRegistry.Beats: fewest OTHER heroes
      already on it, then nearest, then lowest instance id. When every enemy is
      equally covered this collapses back to plain "nearest", so ordinary fights
      look unchanged.

      THE SCENARIO IT FIXES (Arash, from play): hero A spawns and walks at the
      left enemy; hero B spawns on the same side and, being nearest-driven, walks
      at the SAME enemy - while the right-hand enemy reaches the player base
      unopposed. Hero B now crosses to the right enemy although it is far away,
      because nobody else is on it.

  PHASE A - First detection (while !hasEverDetectedEnemy)
      Runs ONE Physics2D.OverlapCircleAll against "EnemyLayer" within
      detectionRadius and picks the best living EnemyStats by the ranking above.
      Radius-limited so a hero still walking in cannot lock onto something on the
      far side of the field before it has seen anything at all. On success sets
      currentTarget/lastKnownTarget and latches hasEverDetectedEnemy = true.

  PHASE B - Persistent search (once hasEverDetectedEnemy is true)
      Calls FindObjectsOfType<EnemyStats>() and ranks ALL living enemies the same
      way. NO radius limit, on purpose: a hero may be sent right across the field
      to cover an enemy nobody else is on, and in the reported case the free
      enemy WAS the far one. If none remain, clears both target fields and
      hasEverDetectedEnemy, dropping back to Phase A next frame.

      Because of rule 1 this now runs only on the frames where a hero has no
      target, not every frame - which incidentally removes most of the cost the
      warning below is about.

  !! PERFORMANCE: Phase B runs FindObjectsOfType<EnemyStats>() - a full scene
  scan allocating an array - EVERY FRAME for EVERY player unit once it has
  found its first target. This is more expensive than EnemyManager's own
  per-frame OverlapCircleAll and is the most significant per-frame allocation
  source among the Combat/Player scripts.

  GetActiveTargetPosition() -> Vector3
      Returns the gate's position if attackPlayerGate is set, else the current
      target's position, else the unit's own position as a safe fallback.

MOVEMENT
--------
  IsInAttackPosition() -> bool     (added 2026-09-11)
      MeleeEngagement.InAttackPosition(self, currentTarget, maxAttackRange).
      TRUE only when the hero is close enough, NOT sunk into its target, and
      level enough with it for the weapon box to overlap. Read by
      PlayerPursueTargetState and PlayerCombatState - they both call THIS, so
      they cannot disagree about whether the hero has arrived.

  IsEngagedWithTarget -> bool  (property, added 2026-09-22)
      "Has this hero JOINED the fight with currentTarget?" TRUE when the target
      is alive AND any of: isPerformingAction / isInteracting (a swing is playing),
      currentState == AttackState (mid-swing), or IsInAttackPosition() (standing
      in melee). FALSE with no target or a dead one.

      WHY IT IS NOT JUST A STATE TEST. A hero in a sustained fight is in
      AttackState only for the frames it STARTS a swing - PlayerAttackState sets
      isPerformingAction and PlayerCombatState holds it until currentRecoveryTimer
      expires - so most of a fight is spent in PlayerCombatState. A state-only
      test would read "not attacking" in precisely the gaps where the 0.5s
      re-balance tick is most likely to land.

      Deliberately excludes attackPlayerGate: a gate engagement is judged on
      currentGateTarget and must not freeze this hero's ENEMY choice.

      Sole consumer: TryRebalance's engagement lock (rule 1b).

  HandleMoveToTarget(bool canMove)
      No-ops if canMove is false or the Rigidbody2D is missing. Bails out on a
      null chosenEnemyOffset ONLY when there is no enemy target (the gate march
      still needs an anchor) - see NOTES.
      Applies CrowdSeparation2D.ResolveOverlap as a positional nudge, resolves
      its own destination with ResolveAttackDestination, and walks there:
      stops dead within 5 cm of it, otherwise bends the direction through
      CrowdSeparation2D.SteerAroundBlockers (allies only) and sets
      linearVelocity = dir * CurrentMoveSpeed, damped 0.7x inside maxAttackRange
      for a cleaner stop.

  ResolveAttackDestination(anchor) -> Vector2      (rewritten 2026-09-11)
      Where this hero walks to fight: BESIDE the target, at standoff distance,
      inside the vertical band where its weapon can reach.
        - Claims an AttackSlotRegistry slot on the target the first time, and
          re-claims (plus resets the held side) whenever the target changes.
          Released in OnDisable.
        - For a GATE target it returns the anchor unchanged. The gate is a wide
          building, not a duellist; walking to one of its flanks would march
          heroes off the side of it.
        - For an ENEMY target the `anchor` (the EnemyOffsetLeft/Right marker
          EnemyStats hands out) is only a hint. The side is re-derived from the
          hero's OWN position through MeleeEngagement.ChooseSide with
          PlayerPreferredSide, so the enemy walking toward this hero arrives at a
          compatible spot instead of the two circling each other. The point comes
          from MeleeEngagement.StandPoint.

      CRITICAL INVARIANT: the returned point must always satisfy
      IsInAttackPosition. The pursue state decides with that predicate while this
      method decides where the mover walks; if the two can disagree the mover
      reports "arrived" and stops, the state reports "not there yet" and keeps
      pursuing, and the hero freezes playing its walk animation. MeleeEngagement
      keeps the point on the standoff circle and inside the band precisely so this
      cannot recur.

  HandleRoamForward()
      The march on the enemy gate once the field is clear. Goes through
      CrowdSeparation2D for both steering and personal space, then writes
      linearVelocity along transform.up at CurrentMoveSpeed. It exists because
      PlayerPursueTargetState used to drive this march with a raw inline
      linearVelocity write that skipped avoidance entirely.

  SetAnimMoving(bool moving)
      Sets the Horizontal/Vertical blend-tree floats, null-safe.

  DELETED 2026-08-21: ApplyFriendlySeparation() and ResolveHorizontalOverlap().
      Both tried to keep units apart and fought each other - one bent the move
      direction so a crowded unit walked sideways instead of at its target, the
      other ran MovePosition every FixedUpdate unconditionally and gave two units
      at the same x the SAME push sign, sliding them along together. Spacing is
      now owned by the scene-level CrowdSeparation2D; attacker spread is owned by
      AttackSlotRegistry + MeleeEngagement.

  REMOVED 2026-09-11: the serialized attackSlotAngleStep / attackStandoffFactor.
      They tuned an arc that fanned attackers AROUND the target, which let a hero
      come to rest directly above or below it. Spacing is now defined once, for
      both factions, in MeleeEngagement.

FixedUpdate()
-------------
  Yields immediately if MeleeContactRecovery.IsRepositioning, then calls
  HandleStateMachine() every physics step - NOT gated by GameplayPause, unlike
  Update(), meaning the state machine keeps ticking during a pause unless the
  individual state itself checks the pause flag (most states do not).
  (ResolveHorizontalOverlap used to be called here too; it was deleted
  2026-08-21.)

  HandleStateMachine()
      currentState.Tick(this, PlayerStats, playerAnimatitorManager) -> if a
      non-null next state comes back, SwitchToNextState(next). This is the
      literal FSM drive loop described in PlayerState's own doc.

  SwitchToNextState(playerState)
      currentState = playerState. No enter/exit hooks - a state's setup logic
      must happen inside its own Tick on first call.

  HandleRecoveryTimer()
      Counts currentRecoveryTimer down; clears isPerformingAction once it
      expires. (Unlike EnemyManager's equivalent, this does not also clear an
      IsAttacking flag - PlayerManager has none.)

DAMAGE
------
  DamageApplying(EnemyManager target) -> float
      CombatMath.DamagePerHit(unitStats, target.unitStats) - the player's
      outgoing damage number, applied by PlayerDamageCollider.

COLLISION
---------
  OnCollisionEnter2D(collision)
      If the other object is tagged "EnemyGate", sets attackPlayerGate = true
      and resolves currentGateTarget from its EnemyGateStats component, logging
      a debug message. This is a COLLISION (not trigger) callback, so it
      requires the gate to have a non-trigger collider that the unit physically
      bumps into.

HOW IT CONNECTS
---------------
  - Every PlayerState's Tick receives this object and drives it through public
    fields: currentTarget, currentGateTarget, canMove, isUnlocked,
    attackPlayerGate, playerRigidbody, moveSpeed, maxAttackRange, etc.
  - PlayerStatsApplier supplies unitStats.
  - TargetDetectionForPlayer is ALSO present on the object but note that
    UpdateTargetSelection here is a SEPARATE, independent target-acquisition
    implementation - the states call targetDetectionForPlayer.EnsureTarget()
    while PlayerManager.Update() runs its own UpdateTargetSelection()
    concurrently. Both write to currentTarget, so two systems race to decide
    the same field every frame (see NOTES).
  - EnemyGateStats.OnGateDestroyed drives HandleGateDestroyed.
  - HudCurrencyView.Instance is touched on gate destruction.

NOTES / RISKS
-------------
  - DUPLICATE TARGETING SYSTEMS: this class's own UpdateTargetSelection() and
    TargetDetectionForPlayer.EnsureTarget() (called from the FSM states) are
    still two independent implementations that both assign
    playerManager.currentTarget, using different search strategies (this one
    scans ALL EnemyStats with no radius limit in Phase B; TargetDetectionForPlayer
    uses a configurable overlap radius with FOV options). They are STILL worth
    consolidating onto one path.

    [2026-09-17] The race they used to run is defused, not removed. Neither path
    may switch a living target any more, and both rank candidates through the
    same TargetClaimRegistry.Beats, so whichever executes last in a frame now
    reaches the same answer. Before stickiness the last writer simply won, and
    neither file made that visible.
  - UpdateTargetSelection's Phase B is a full-scene FindObjectsOfType scan, and
    it used to run every frame for every unit. [2026-09-17] Rule 1 means it now
    runs only on the frames where a hero has NO target - at spawn and after its
    enemy dies - so the per-frame O(units * enemies) cost is largely gone. It is
    still the expensive path when a whole wave dies at once.
  - [2026-08-21] RESOLVED: the two concurrent anti-overlap systems
    (ApplyFriendlySeparation inside movement, and the separate
    ResolveHorizontalOverlap in FixedUpdate) are both gone. Spacing is owned by
    CrowdSeparation2D; attacker spread by AttackSlotRegistry + MeleeEngagement.
  - A dead numbered sibling HandleGateDestroyed1() remains - differs from the
    live version mainly in explicitly calling ChangeStateSafe with a comment
    referencing a "real state-switch method name", suggesting an in-progress
    refactor that was completed in the live version and left behind here.
  - UpdateFacingAndOffset1() is another unused numbered sibling with a nearly
    identical but slightly different (no dead-zone) implementation.
  - enemyStats (private field) is assigned in Awake via a scene-wide
    FindAnyObjectByType call but is never read anywhere in the class - a dead
    lookup that still costs a scene search on every unit's Awake.
  - [2026-08-20] FIXED: the line `unitStats = playerStatsApplier.CurrentStats;`
    used to run UNCONDITIONALLY. PlayerStatsApplier.ApplyNow() returns early and
    leaves CurrentStats NULL whenever GameStartManager / PlayerUnits is missing,
    which is exactly what happens when a gameplay scene is played DIRECTLY
    instead of booting through StarterScene. That null then overwrote the
    perfectly good serialized UnitStatsRuntime, and the next enemy hit on the
    player gate threw a NullReferenceException inside CombatMath.DamagePerHit.
    It now only adopts CurrentStats when non-null, falls back to a fresh
    UnitStatsRuntime, and logs a warning naming the object.
    NOTE this is a resilience fix, not a substitute for booting properly - a
    unit that keeps its serialized zeros still has no real stats.

  - [2026-09-11] MELEE UNITS NOW ENGAGE FROM THE SIDE, NOT FROM ABOVE OR BELOW.
    Reported bug: with a hero and an enemy in the same lane, neither could damage
    the other and the two sprites merged. Cause: every melee hitbox in the project
    is a wide flat trigger on a weapon bone that only reaches SIDEWAYS
    (Player_Valkyrie's sword box is ~1.46 x 0.24 in world units, offset +0.78 on
    X), while both sides decided "I have arrived" from a bare radial distance,
    which cannot tell "beside" from "on top of". Three files changed on the hero
    side - IsInAttackPosition + the rewritten ResolveAttackDestination here,
    PlayerPursueTargetState and PlayerCombatState - plus the mirror-image fix in
    EnemyLocoMotion / EnemyManager. See MeleeEngagement.txt for the geometry, the
    invariant, and the two-body stability argument.

  - [2026-09-11] HandleMoveToTarget's null-anchor bail-out is now conditional, and
    that mattered: UpdateFacingAndOffset only assigns chosenEnemyOffset once the
    target is at least facingDeadZoneX (0.12) off-centre, so a hero that acquired
    a target sitting DEAD LEVEL above it never got an anchor at all - and then
    never took a step. Exactly the alignment this whole fix is about.
